## Что сделать

Три уровня доступа роли к группе полей: «видно и можно менять» (`edit`), «только чтение» (`read`), «скрыто» (`hidden`) — `FIELD_GROUP_ACCESS` в `packages/shared/src/permissions.ts`.

Каталог прав:

- `parsePermissions` сейчас требует пустой `fieldGroups`. Теперь он принимает `{ id группы: доступ }` с доступом из `FIELD_GROUP_ACCESS`; сервер дополнительно проверяет, что каждый id — группа этого проекта. Группа без записи — по правам части системы её сущности: `edit`, если роль может изменять сделки (контакты, организации), иначе `read`. Удалённая группа убирается из прав всех ролей.
- Роль «администратор» всегда имеет `edit` на все группы; записать ей `read` или `hidden` — 422 (роль администратора нельзя урезать).
- Защита от расширения прав (`apps/api/src/roles/guard.ts`): не-администратор не выдаёт роли доступ к группе выше своего (`edit` > `read` > `hidden`); проверяется только добавляемое, как для остальных прав.
- Одна функция «доступ роли к группе» и «какие коды поля роль видит / может менять» для всего сервера.

Где скрытое не отдаётся (здесь — для API тикетов 01 и 02 и для истории; список, фильтры, выгрузку и канбан подключает тикет 07):

- описания: `/api/v1/field-groups` и `/api/v1/fields` не возвращают скрытые группы и их поля;
- значения: из `custom` в ответах сделки, контакта и организации убираются коды скрытых полей;
- история: записи `change_log` по скрытым полям не отдаются ни в ленте, ни в ответах истории;
- запись: поле группы `read` — 403; поле группы `hidden` — 422 как неизвестный код, чтобы ответ не выдавал существование поля (решено без владельца, подтвердить). Значения скрытых полей при изменении записи не теряются.

Экран: в редакторе ролей («Налаштування → Ролі») раздел «Групи полів» — таблица групп по сущностям с выбором доступа; у администратора — только `edit`, без выбора. Тот же запрос использует диалог группы в конструкторе (тикет 05).

Тикет не отправляет событий (ADR 0003).
