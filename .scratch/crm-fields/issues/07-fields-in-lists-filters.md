## Что сделать

Фильтры. Добавить пользовательские поля в единый формат условий и функцию построения запроса эпика `crm-deals` (`packages/shared/src/filters/`, `apps/api/src/filters/`) — тот же формат принимают список, канбан, сохранённые фильтры и выгрузка. В условии поле указывается по id; запросы `/api/v1` принимают и код (`custom.<код>`). Операции по типам:

| Типы | Операции |
|---|---|
| текст, большой текст, телефон, email, ссылка, адрес | содержит, равно, пусто, не пусто |
| число, деньги (сумма и валюта), дата, время | =, <, >, между, пусто, не пусто |
| интервал дат | начало и конец: <, >, между; пусто |
| один вариант, несколько вариантов | любой из, ни один из, пусто, не пусто |
| да/нет | да, нет, пусто |
| пользователь | я, любой из, пусто, не пусто |

Значения сравниваются в приведённом виде тикета 02 (телефон в условии тоже приводится к E.164).

Права в фильтрах и выдаче (функция доступа тикета 03): поле скрытой от пользователя группы нельзя выбрать в условии, колонке, сортировке и выгрузке; запрос с ним — 422 как неизвестный код. Условие сохранённого фильтра по архивному полю или по полю, скрытому от того, кто открыл фильтр, не применяется, фильтр показывает пометку «умова недоступна» (решено без владельца, подтвердить).

Список и выгрузка: пользовательские поля можно выбрать колонками и сортировать по ним; выгрузка в CSV включает выбранные видимые колонки, значения вариантов и пользователей — названиями. Быстрый поиск по пользовательским полям не ищет (решено без владельца, подтвердить).

Карточка канбана: в настройках воронки («Налаштування → Воронки») администратор выбирает до 3 полей сделки, видимых в этой воронке, для показа на карточке канбана (для каждой воронки отдельно — решено без владельца, подтвердить); выбор хранится у воронки, четвёртое — 422. Пустое поле на карточке не показывается; скрытое от роли — тоже. Выдача канбана отдаёт значения только этих полей.

Индекс «часто фильтруют»: отметка у поля (тикет 01) ставит фоновую задачу pg-boss, которая строит для поля отдельный индекс `CREATE INDEX CONCURRENTLY` по выражению значения с приведением к типу (текст, число, дата) и условием `project_id = <проект>`; снятие отметки, архив и окончательное удаление поля индекс убирают. Роль приложения не владеет таблицами, поэтому задача выполняет DDL служебной ролью-владельцем, вне `withProject`; имя индекса выводится из id поля. Состояние у поля: строится / готов / ошибка (с текстом), его показывает конструктор (тикет 05). Функция построения запроса использует ровно то выражение, по которому построен индекс.

Ограничение PostgreSQL, найденное в тикете 02 (проверено планом запроса на PostgreSQL 18.6): функции `jsonb_contains` (оператор `@>`) и `jsonb_object_field_text` (оператор `->>`) не помечены LEAKPROOF. Поэтому под row-level security роль приложения `alpi_app` применяет такое условие фильтром после политики проекта и не использует ни GIN-индекс `custom` из тикета 02, ни частичный индекс по выражению `(custom->>'код') where project_id = <проект>`: у `alpi_app` — `Seq Scan`, у владельца таблицы те же запросы идут `Bitmap Index Scan`. Схему индекса и запроса фильтра нужно выбрать так, чтобы индекс работал именно у `alpi_app` внутри `withProject` (обёртка LEAKPROOF требует суперпользователя; другие варианты — отдельная таблица значений или сгенерированные столбцы); выбор — решение этого тикета, с проверкой плана.

Тикет не отправляет событий (ADR 0003).

## Результат

- Формат условий (`packages/shared/src/filters/`): поле условия — `custom.<id>` (сервер хранит и отдаёт по id), запросы `/api/v1` принимают и `custom.<код>`; у интервала дат — `custom.<id>.start` / `.end`. Новый оператор `between` со значением `[от, до]` (от ≤ до) — только у пользовательских полей. Операторы по типу — `customOperators` (таблица тикета); телефон в «равно» приводится к E.164, email — к нижнему регистру. Колонки и сортировка — `custom.<id>`; «несколько вариантов» не сортируется.
- Права: каталог полей пользователя (`apps/api/src/filters/custom.ts`, `loadFilterCatalog`) — действующие поля сущности, видимые роли. Поле вне каталога (неизвестный код, архив, скрытая группа) в условии, сортировке и колонке выгрузки — 422 `CUSTOM_FIELD_UNKNOWN` тем же телом. Массовая операция по фильтру проверяет условия по каталогу при выборке записей и падает, а не расширяет выборку.
- Сохранённые фильтры: при чтении условия по полям вне каталога того, кто открыл, убираются (`withoutUnavailable`; опустевшая вложенная группа уходит целиком — пустая группа внутри «или» дала бы все записи), в ответе — `unavailableConditions`; список показывает «умова недоступна». Сохранить фильтр с недоступным полем нельзя — 422.
- Выгрузка CSV: колонки `custom.<id>`, заголовок — название поля на языке выгрузки, варианты и пользователи — названиями, деньги — «сумма валюта», интервал — «від — до», да/нет — словами.
- Карточка канбана: таблица `pipeline_card_field` (до 3 полей, позиция 1…3 проверяется базой), `GET/PUT /api/v1/pipelines/:id/card-fields` (`apps/api/src/pipelines/card-fields.ts`): поле должно быть действующим полем сделки, видимым в воронке и роли, иначе 422 `CUSTOM_FIELD_UNKNOWN`; четвёртое — 422 `TOO_MANY_CARD_FIELDS`; изменение пишет `pipeline.updated` с полями до и после. Выдача канбана — `GET /deals?view=kanban&pipeline=…`: в `custom` только поля карточки, видимые роли. Экран: «Налаштування → Воронки» — три выбора на воронку; под карточкой сделки — непустые значения. Поля выводятся под карточкой, а не внутри: компонент карточки (`components/deal-card`) вне файлов тикета.
- Экран списков: условия по полям в редакторе фильтра (поля из `GET /fields`), колонки и сортировка по полям, пометка недоступного условия у сохранённого фильтра; то же у контактов и организаций (общий `ListView`).

Решено без владельца — подтвердить:

- **Ускорение «часто фильтруют» — не `CREATE INDEX CONCURRENTLY`, а копия значений.** Индекс по выражению над `custom` роль приложения не использует в принципе: функции `jsonb` не LEAKPROOF, и под RLS условие идёт фильтром после политики. Поэтому (миграция `0018_field_filters`): таблица `custom_value` (проект, поле, запись, часть, `value_text` / `value_number`) с RLS проекта и индексами `(field_id, part, value_text…)` и `(field_id, part, value_number)` — сравнения `text` и `float8` LEAKPROOF, и план роли `alpi_app` в `withProject` идёт по индексу (проверено `EXPLAIN` на 100 тыс. сделок: `custom_value_number_idx`). Фильтр по полю в состоянии «готово» добавляет к условию по `custom` (источник истины) `id in (select record_id from custom_value …)`. Копию держит триггер базы `custom_value_sync` на `deal`, `contact`, `organization` — срабатывает при любой записи, и через API, и в обход (массовые операции, задачи, SQL). Отметка поля переводит его в «строится» (триггер `field_definition_index`), задача pg-boss `field-index` (`apps/api/src/jobs/field-index.ts`) порциями копирует значения ролью приложения и ставит «готово»; ошибка — «ошибка» с текстом. Снятие отметки, архив и удаление поля убирают копию; восстановление строит заново. DDL в работе приложения нет, служебная роль-владелец не нужна.
- Цена решения: каждая запись `custom` отмеченного поля — ещё удаление и вставка строк копии в той же транзакции (триггер работает и для неотмеченных полей, но строк не пишет); значения отмеченных полей хранятся дважды; текст длиннее 200 символов в копию не попадает (значение условия тоже не длиннее 200, так что «дорівнює» его и не нашёл бы, а «містить» идёт по `custom`); копия ускоряет «дорівнює», «менше», «більше», «між» и «одне з»; «містить», «порожнє», «заповнене» и «жодне з» идут по `custom` без ускорения.
- Пока копия строится или после ошибки фильтр работает по `custom` без ускорения — результат тот же, медленнее.
- Условие сохранённого фильтра по недоступному полю убирается молча (пометка в списке), сам фильтр применяется без него.
- Поля карточки канбана — у каждой воронки свои.
- Быстрый поиск по пользовательским полям не ищет.
