## Что сделать

`pnpm seed` заполняет локальную базу выдуманными данными для разработки, ручной проверки и приёмки (тикет 16). Работает служебной ролью, отказывается запускаться, если `NODE_ENV=production` или адрес базы не локальный без явного флага.

- Проект ALPI: стартовая настройка тикета 02 (3 воронки, этапы, причины проигрыша); 10 менеджеров в 2 командах по 5 (тимлид каждой команды — один из пяти) с ролями из шаблонов; администратор для входа; 4 000 контактов; 5 000 сделок. Распределение похоже на настоящее: большинство сделок воронки «ALPI» на «Новий лід» с нулевой суммой, суммы на этапах брони и счёта; часть сделок выиграна, часть проиграна с причинами, часть в архиве, часть без ответственного (общая очередь), часть в воронке «Платформа (допродаж)» у контактов с выигранной сделкой. Каталог из нескольких товаров с ценами в трёх валютах, строки у части сделок.
- Проект «Франч»: стартовая настройка «Франч», 300 сделок с организациями, у части сделок участники с ролями, суммы в EUR с этапа «Встреча проведена».
- Всё выдуманное: имена из генератора с фиксированным зерном, телефоны украинского формата из диапазона, который не выдаётся абонентам (или с явной тестовой меткой), email только на домене `example.com`. Никаких данных из Pipedrive, кроме названий воронок, этапов и причин.
- Правило «одна открытая сделка у человека в воронке» соблюдается; данные создаются через те же функции, что и API, либо проверяются ими после вставки.
- Идемпотентность: повторный запуск не создаёт дублей (записи помечаются внешней ссылкой `external_link` с системой `seed`), а `pnpm seed --reset` удаляет только данные, созданные командой.
- Учётные данные пользователей для входа (пароль и секрет 2FA для тестов) печатаются в консоль и пишутся в локальный файл вне git.

Тикет не отправляет событий (ADR 0003); экранов нет.

## Результат

- `pnpm seed [--scale <доля>] [--allow-remote]` и `pnpm seed --reset` — `apps/api/src/cli/seed.ts`; данные — `apps/api/src/seed/` (план `plan.ts`, запись `store.ts`, пользователи `users.ts`, генератор `random.ts`, имена `names.ts`). Тест — `apps/api/src/cli/seed.test.ts` (масштаб 0,1: 400 контактов и 500 сделок ALPI, 30 сделок «Франча»).
- Запись — служебной ролью (MIGRATION_DATABASE_URL) прямо в таблицы, затем тест читает созданное через API под менеджером (`GET /v1/deals/:id`: свои и общая очередь — 200, чужие — 404). Не через HTTP API (5 000 сделок по одной) и без выноса функций других модулей — **решено без владельца, подтвердить**. Правила базы (одна открытая неархивная сделка у человека в воронке, этап своей воронки, действующая причина) действуют при вставке; сделку плана, которая нарушила бы правило из-за записи, созданной руками, seed пропускает и пишет об этом.
- Генератор с зерном — самописный mulberry32 (`random.ts`), без новой зависимости; зерно по умолчанию `20261123`.
- Телефоны — `+380 70 XXXXXXX`: код 70, насколько известно, абонентам не выдан (по плану нумерации НКЕК не сверено). Email — только `@example.com`; пользователи — `seed.admin@example.com`, `seed.manager01…10@example.com`.
- Пользователи заводятся через Better Auth, 2FA включается тем же путём, что в браузере (вход, включение, код). Пароль случайный; пароли и секреты 2FA печатаются и пишутся в `.seed-credentials.json` в корне репозитория (в `.gitignore`). Нужны те же переменные, что у API (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`): секрет 2FA шифруется ключом API.
- Защита: `NODE_ENV=production` (без учёта регистра и пробелов) — отказ всегда (и для `--reset`). Хост базы берётся так, как его выберет `pg` (`parse()` из pg-connection-string: `?host=`, пустой хост → PGHOST → localhost); локальными должны быть он, PGHOST, `hostaddr` и PGHOSTADDR — разрешены localhost, 127.0.0.1, ::1 и unix-сокет, иначе отказ без `--allow-remote`. pg-connection-string 2.14.1 (уже стоял как зависимость `pg`) стал прямой зависимостью `@alpi/api`.
- Повторный запуск: всё созданное помечено `external_link` (система `seed`, ключ записи из плана) и досоздаётся только недостающее. Проект с кодом `alpi` или `franch`, созданный не командой, — отказ до любых записей.
- `--reset` — **решено без владельца, подтвердить**: удаляет помеченные сделки, контакты, организации и товары. Остаётся запись seed, на которую ссылается запись, созданная не командой: сделка с ручной заметкой, файлом, строкой товара или участником; контакт с ручной заметкой, файлом, сделкой или участием в сделке; организация с ручной заметкой, файлом, сделкой или контактом; товар в ручной строке. Строки товаров и участники, созданные seed, тоже помечены `external_link`, чужие считаются ручными. Сколько записей seed оставлено, команда печатает. Проект seed удаляется целиком только если в нём не осталось записей не от seed (иначе остаются проект, его настройка, участники и команды). Пользователи seed удаляются вместе со своими записями журнала входов (`system_audit_log`) — вопреки правилу «пользователей не удаляют, а банят», раз это тестовые учётные записи; пользователь, на которого ещё ссылаются (участник оставленного проекта, автор заметки), остаётся. Файл учётных данных дописывается после каждого созданного пользователя и не попадает в образы (`.dockerignore`).
- «Франч» ведут три менеджера ALPI (`manager02`, `manager03`, `manager07`) с ролью «менеджер» — **решено без владельца, подтвердить**.
- Полный запуск (масштаб 1) на локальном embedded PostgreSQL через CLI: 11 пользователей, ALPI — 4 000 контактов и 5 000 сделок, «Франч» — 300 сделок, 255 организаций, 389 контактов; 4,0 с внутри команды, 6,5 с с запуском pnpm (после доработки; в первом раунде 6,3 с); повторный запуск — 0,1 с, числа записей не изменились. Под `seed.manager02` все 5 000 сделок ALPI через API: свои 443 и очередь 734 — 200, чужие 3 823 — 404, расхождений 0.
