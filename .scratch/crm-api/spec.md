# Эпик: API для автоматизации и события

Четвёртый эпик реализации CRM; по карте `.scratch/crm-build/map.md` идёт сразу за эпиками `crm-deals` и `crm-fields`. В разделе 12 спецификации MVP ([`.scratch/crm-mvp/spec.md`](../crm-mvp/spec.md)) такого эпика нет: он появился из решения владельца «CRM сама сделки не меняет» — [`docs/adr/0003-crm-ne-menyaet-sdelki-sama.md`](../../docs/adr/0003-crm-ne-menyaet-sdelki-sama.md) и ответов 13.0.4 спецификации. Состав, волны и все правила ниже, кроме помеченных, утверждены владельцем 2026-11-04 в тикете-решении [`.scratch/crm-build/issues/03-automation-api-contract.md`](../crm-build/issues/03-automation-api-contract.md) (раздел «Answer»). Как надёжно доставлять события — исследование [`.scratch/crm-build/issues/04-webhook-delivery-research.md`](../crm-build/issues/04-webhook-delivery-research.md), отчёт `docs/research/webhook-delivery.md` на ветке `origin/research/webhook-delivery` (коммит 553ca65, не сливается; читать `git show origin/research/webhook-delivery:docs/research/webhook-delivery.md`). Термины — `GLOSSARY.md` («Ключ API», «Событие», «Внешняя автоматизация»); изоляция проектов — `docs/adr/0001-izolyatsiya-proektov.md`.

Зачем эпик: CRM ничего не делает со сделкой сама. Двигает сделки по этапам, выигрывает их, назначает ответственных и архивирует внешняя автоматизация владельца (n8n, Make или свой сервис). Ей нужны две вещи: **ключ API** — доступ к одному проекту с ролью этого проекта, и **события** — подписанные сообщения (исходящие вебхуки), которые CRM отправляет на адрес автоматизации, когда что-то произошло.

Готово, когда: администратор проекта создаёт ключ API с ролью, и внешняя программа с этим ключом создаёт и ведёт сделку через `/api/v1` ровно в пределах прав роли и только в своём проекте; на адрес из настроек приходят подписанные по Standard Webhooks события о сделках и контактах, с повторами при сбое и журналом доставок; событие, вызванное запросом по ключу, называет этот ключ автором, и автоматизация не зацикливается на своих изменениях; сценарий приёмки проходит автотестом локально и в CI; `pnpm verify` и CI зелёные.

## Входит

- Ключи API проекта: создать (название и роль), секрет показывается один раз, в базе — только отпечаток; отозвать, перевыпустить, срок действия по желанию; `Authorization: Bearer …`. Запрос по ключу идёт тем же путём, что запрос пользователя: изоляция проекта в базе (row-level security), проверка прав роли и охвата. Действия по ключу видны в журнале под названием ключа. Экран «Налаштування → Ключі API».
- Общие правила `/api/v1`: JSON; ошибки в формате RFC 9457 (problem details) с кодом и полем; курсорная постраничная выдача; заголовок `Idempotency-Key` против дублей при повторе запроса; 600 запросов в минуту на ключ (429 и `Retry-After`); описание API в формате OpenAPI, построенное из кода, на `/api/v1/docs`.
- Запросы для ключей. Сделки: создать, изменить поля и сумму, сменить этап, ответственного, выиграть, проиграть с причиной, открыть заново, архивировать, перенести в другую воронку. Удаления нет. Контакты и организации: создать, изменить, найти по телефону или email. Заметки. Справочники только для чтения: воронки, этапы, причины проигрыша, пользователи, команды.
- События: строка события пишется в той же транзакции, что изменение (шаблон transactional outbox — таблица исходящих событий, очередь pg-boss через `fromKysely(trx)`). Каталог этого эпика — сделки и контакты. Тело тонкое: id, тип, время, id сущности, что изменилось, кто сделал (пользователь или ключ).
- Доставка: вебхук — адрес, подписанный на выбранные типы; подпись Standard Webhooks v1; доставка «хотя бы один раз», порядок не обещается; повторы около 3 суток; отключение адреса при `410` или после 5 суток без успеха с уведомлением администратору; журнал доставок 30 дней; ручная повторная отправка; защита от запросов во внутреннюю сеть через адрес (SSRF). Экран «Налаштування → Вебхуки».
- Приёмка автотестом: тестовый приёмник проверяет подписи, получает события и двигает сделку через API ключом, не зацикливаясь.

## Не входит

- События регистраций, платежей, звонков и задач (`registration.created` — так решено в эпике `crm-intake` 2026-11-26, раньше здесь было `registration.added`; `payment.succeeded`, `payment.refunded`, `call.completed`, `call.missed`, `task.created`, `task.completed`) и запросы к этим сущностям. Их добавляют эпики приёма, платежей, Unitalk и задач по образцу этого эпика: та же функция записи события в транзакции, тот же формат тела, тот же список запросов, доступных ключу.
- Ключи источников регистраций (`intake_source`, `POST /api/intake/registrations`) — эпик приёма; это другой вид ключа с другим адресом.
- Удаление и восстановление через API, корзина, «взять в работу», допродажа, участники сделки, строки товаров, файлы, массовые операции, выгрузка — только по сессии пользователя (решено без владельца — подтвердить; в решении владельца их нет).
- Управление ключами, ролями, участниками и адресами событий через API — только по сессии пользователя в интерфейсе.
- Строгий порядок событий одной сделки (политика очереди `key_strict_fifo`) — включается позже, если владелец попросит.
- Подпись открытым ключом (вариант `v1a` Standard Webhooks), свои заголовки на адресе (например статический `Authorization`) — не в MVP (решено без владельца — подтвердить).
- Любая автоматика: CRM не двигает сделки и не назначает ответственных сама (ADR 0003).

## Общие правила для всех тикетов

- Каждый запрос — под `/api/v1/...`, внутри контекста проекта (`withProject`, row-level security) и за `requirePermission(часть системы, действие)` с условием охвата (`apps/api/src/roles/scope.ts`). Для ключа проект и роль берутся из ключа, а не из сессии и заголовка `X-Project-Id`; дальше путь тот же.
- Ключ проходит только на маршруты, явно отмеченные «доступно ключу» (список ведут тикеты 03 и 04; эпики приёма, платежей, Unitalk и задач дополняют его). Остальные маршруты отвечают ключу 403 при любой роли (решено без владельца — подтвердить).
- Каждая новая таблица данных проекта — с `project_id` и политикой RLS, как в `packages/db/migrations/0001_project_isolation.ts`; у роли приложения нет BYPASSRLS. Поиск ключа по отпечатку до того, как известен проект, — узкой функцией `SECURITY DEFINER`, как в `packages/db/migrations/0003_projects.ts`. В «Done when» тикета с данными — тест изоляции и тест прав.
- Номер миграции не закреплён за тикетом: каждый берёт следующий свободный номер миграции в момент слияния.
- По ADR 0003 действие меняет ровно то, что в нём сказано: смена суммы не двигает и не выигрывает сделку, смена этапа не меняет статус. Обязательные поля с этапа (тикет 04 эпика `crm-fields`) действуют для ключа так же, как для менеджера.
- Пользовательские поля в запросах и ответах — по их коду (`custom: { код: значение }`), с правами роли ключа на группы полей: скрытые группы в ответ не попадают.
- Изменения пишутся общей функцией истории `change_log` эпика `crm-deals` с автором — пользователем или ключом; события ключей и опасные действия — функцией `apps/api/src/audit/record.ts`.
- Фоновые задачи — pg-boss из тикета 04 эпика `crm-deals`; задача данных проекта выполняется внутри `withProject`.
- Тексты интерфейса — украинский и русский (`apps/web/src/i18n/locales/{uk,ru}`); экраны на компонентах основы дизайна (тикет 01 эпика `crm-deals`) и работают на 375 px.
- В примерах, тестах и описании API — только выдуманные данные, без персональных данных и реальных имён.

## Проверка безопасности

Тикеты 01 (ключи), 03 (запросы сделок по ключу) и 06 (доставка: секреты, SSRF) помечены в заголовке строкой `Risk: high`: перед слиянием их ветку смотрит расширенный обзор. Тикетам 01, 02, 03, 04 и 06 при проверке нужна линза безопасности (`security`) — это сказано в каждом из них.

## Решения эпика (приняты без владельца — подтвердить)

Всё остальное взято из решения владельца и исследования. Ниже — пробелы, закрытые допущениями; каждое помечено и в своём тикете.

Ключи (тикет 01):

- Создавать, отзывать и перевыпускать ключи может пользователь, у роли которого есть и «интеграции» (`integrations`: создавать, изменять, удалять), и «пользователи и роли» (`users_roles`: изменять): выдать ключу роль — то же, что выдать её участнику. По шаблонам ролей это только администратор.
- Секрет — `alpi_` и 32 случайных байта в base64url; в базе — SHA-256 секрета и первые 8 символов для показа в списке.
- Перевыпуск сразу делает старый секрет недействительным, без переходного периода.
- Название ключа после создания не меняется — журнал всегда показывает то же имя.
- Охват роли «свои» или «команда» для ключа даёт только сделки общей очереди (у ключа нет своих сделок и команды); экран предупреждает, если у выбранной роли охват не «все».
- Запрос с `Authorization: Bearer` считается запросом ключа, cookie сессии в нём не читается. `X-Project-Id` не нужен; если передан и не совпадает с проектом ключа — 403.
- Неизвестный, отозванный и истёкший ключ получают одинаковый ответ 401, чтобы ответ не выдавал, существовал ли ключ.
- Роль, на которой есть действующий ключ, удалить нельзя (409).
- Журнал: каждое изменяющее действие по ключу пишется и в историю записи (`change_log`, автор — ключ), и в журнал действий проекта (`audit_log`) с названием ключа; создание, отзыв и перевыпуск ключа — в журнал опасных действий.

Общие правила (тикет 02):

- `Idempotency-Key` принимается у `POST` и `PATCH`; ответ хранится 24 часа; область ключа — автор запроса (ключ API или пользователь) в проекте. Тот же ключ с другим телом или адресом — 422; ответы 5xx не сохраняются, такой запрос можно повторить.
- Счётчик 600 запросов в минуту — в памяти процесса API (в MVP процесс один); при нескольких процессах счётчик переезжает в базу.
- Описание API (`/api/v1/openapi.json` и страница `/api/v1/docs`) открыто без входа и описывает только маршруты, доступные ключу; данных в нём нет.
- Ошибки по RFC 9457 действуют на все маршруты `/api/v1`, в том числе для сессии; поле `code` остаётся, поэтому клиент `apps/web` читает ошибку по-прежнему.
- Курсор: `?limit=` от 1 до 200, по умолчанию 50; ответ `{ data, next_cursor }`; существующие списки эпиков `crm-deals` и `crm-fields` приводятся к нему. Повтор по `Idempotency-Key` помечается заголовком `Idempotent-Replayed: true`; ответы ключу несут заголовки `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`.

Запросы (тикеты 03, 04):

- Назначить, сменить или снять ответственного ключом можно только с правом «передача сделок» (`transfer_deals`) — даже на сделке общей очереди.
- Заметки по ключу: создать и прочитать; изменить и удалить свою заметку ключ может, чужую — нет. Файлов через ключ нет.
- Список пользователей для ключа: id, имя, команда, активен ли; email — только если у роли есть «пользователи и роли: смотреть».

События (тикет 05):

- Перенос в другую воронку — событие `deal.stage_changed` с воронкой и этапом «из» и «в»; отдельного типа нет.
- Кроме «в архив» (`deal.archived`) есть и «из архива» (`deal.unarchived`).
- Автор в событии — только тип и id (`{"type": "user" | "api_key", "id": …}`), без имени: имя пользователя — персональные данные.
- События пишутся для действий из интерфейса, по ключу и из фоновых задач (массовый архив, передача сделок) — автор там инициатор операции.

Доставка (тикет 06):

- Защита адресов: только `https://`; адрес, который разрешается в частную, внутреннюю, локальную (loopback), link-local, CGNAT, multicast-сеть или адрес метаданных облака, отклоняется при сохранении и проверяется снова перед каждой отправкой; редиректы не выполняются. Для автотестов — переменная окружения, разрешающая `http://localhost`; в production с ней API не запускается.
- Секрет адреса хранится в базе зашифрованным ключом из окружения (AES-256-GCM), как секреты интеграций (раздел 9.2 спецификации MVP): его нужно читать, чтобы подписывать.
- Смена секрета: 24 часа события подписываются и новым, и старым секретом (две подписи в заголовке, как разрешает Standard Webhooks).
- `webhook-id` — id события; он одинаков при всех повторах и при ручной повторной отправке.
- Уведомление администратору при отключении вебхука: пока в CRM нет уведомлений (их строит эпик задач), это предупреждение в шапке для пользователей с правом «интеграции» и отметка на экране «Вебхуки»; плюс запись в журнал проекта.
- Ручной повтор: одной доставки и «всё неудачное с даты» для вебхука. События за время, пока вебхук был отключён, догоняет отдельный запрос «догнать события с даты» — тикет 09 (решение владельца 2026-11-26).
- Отключение вебхука: ответ 410 — сразу; 5 суток подряд без успешной доставки при попытках — серия неудач начинается заново, если с последней неудачи прошло больше 24 ч (решение владельца 2026-11-26; docs/adr/0004-dostavka-sobytiy-vebhukami.md).
- Повторы — встроенные pg-boss: `retryLimit: 20`, `retryDelay: 10`, `retryBackoff`, `retryDelayMax: 6 ч` — около 2,5–3 суток (расчёт исследования, прогоном не проверен).

Экран (тикет 07) и волны:

- Экран «Вебхуки» открывается по праву «интеграции» (`integrations`).
- Тикет 07 стоит в волне 3 вместе с 06, но начинается после слияния 06: экран работает на его запросах.

## Расхождения источников

Найдены при подготовке эпика; эпик следует решению владельца (тикет 03 карты `crm-build`), остальное — на подтверждение.

- Раздел 6.x спецификации MVP («Исходящие вебхуки», решено без владельца) называет события «сделка изменена», «задача изменена», «платёж изменён». Его заменили ответы 13.0.4 и решение владельца с подробным каталогом, но раздел 6.x не помечен устаревшим.
- Эпики `crm-deals` и `crm-fields` требуют «каждый запрос под `/api/v1`», а маршруты фундамента (`/roles`, `/members`, `/audit`, `/projects` в `apps/api/src/app.ts`) сейчас без этого префикса и отвечают ошибкой `{ code }`, а не RFC 9457. Тикет 02 приводит к общим правилам только `/api/v1`; переносить ли маршруты фундамента — подтвердить.
- «Уведомление администратору» при отключении адреса нужно сейчас, а уведомления в CRM строит эпик задач (эпик 4 раздела 12 спецификации MVP). До него — предупреждение в шапке (тикет 06).
- `audit_log.actor_id` и автор `change_log` ссылаются только на пользователя; автор-ключ требует новой колонки (тикет 01).
- Ключи источников регистраций (`intake_source`, раздел 6.1 спецификации MVP) и ключи API — два разных вида ключей; в `GLOSSARY.md` есть только «Ключ API». Стоит добавить в глоссарий «Ключ источника регистраций».
- В эпике `crm-deals` смена ответственного на другого требует права «передача сделок», а «взять в работу» ставит ответственным себя; у ключа «себя» нет, поэтому любое назначение ключом требует «передачи сделок» (решение эпика выше).
- Исследование не проверило pg-boss на PostgreSQL 18 и ключ HMAC в n8n и Make; пакет `standardwebhooks` 1.1.1 на npm ещё без исправления разбора заголовка подписи (PR #343) — для тестов это не мешает.

## Зависимость от эпиков `crm-deals` и `crm-fields`

Эпик начинается, когда эпики `crm-deals` и `crm-fields` слиты в main целиком, включая их приёмку (тикет 16 эпика `crm-deals`, тикет 09 эпика `crm-fields`). Это зависимость между эпиками; формат `Blocked by:` ссылается только на номера своего эпика, поэтому у тикетов 01 и 02 в заголовке `Blocked by: —`, а условие записано здесь и в тексте тикетов. К началу есть и используются, а не строятся заново:

- роли, права, охват, команды, журнал (`audit_log`, `apps/api/src/audit/record.ts`) — эпик `crm-foundation`;
- воронки, этапы, причины проигрыша (тикет 02 эпика `crm-deals`); контакты, организации, поиск контакта по нормализованному телефону и email, история `change_log` (тикет 03); фоновые задачи pg-boss (тикет 04);
- сделки и запросы `/api/v1/deals` со сменой этапа, выигрышем, проигрышем, повторным открытием, архивом, переносом, правилом «одна открытая сделка» (тикет 05); заметки (тикет 07); курсорная выдача списков (тикеты 11, 12); набор `pnpm e2e` и задание CI (тикет 16);
- значения пользовательских полей по коду (тикет 02 эпика `crm-fields`), права на группы полей (тикет 03), обязательные поля с этапа для любого пути, включая API (тикет 04).

Все эти запросы до эпика работают только по сессии пользователя и событий не отправляют; этот эпик открывает их ключу и добавляет события.

## Приёмка владельцем

Сценарий, который тикет 08 превращает в автотест (локально и в CI), а владелец проходит руками на тестовых данных `pnpm seed`:

1. Войти администратором ALPI. В «Налаштування → Ключі API» создать ключ «Автоматизація (тест)» с ролью, где есть сделки и передача сделок; скопировать секрет — второй раз он не показывается.
2. В «Налаштування → Вебхуки» добавить вебхук с адресом тестового приёмника, подписать его на «сделка создана», «этап изменён», «сделка выиграна»; скопировать секрет подписи.
3. Менеджером создать сделку. Приёмник получает `deal.created` с автором-пользователем, подпись сходится.
4. Приёмник в ответ ключом переводит сделку на следующий этап запросом `/api/v1`. Приходит `deal.stage_changed` с автором — этим ключом; приёмник его пропускает и больше ничего не делает.
5. Приёмник один раз отвечает 500: событие приходит повторно с тем же `webhook-id`; в журнале доставок видны обе попытки. Ручной повтор из журнала доставляет событие ещё раз.
6. Отозвать ключ: следующий запрос приёмника получает 401.
