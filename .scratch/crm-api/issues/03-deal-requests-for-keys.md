## Что сделать

Запросы сделок уже есть в эпике `crm-deals` (тикет 05) и работают по сессии. Тикет открывает ключу API ровно действия из решения владельца, описывает их в OpenAPI (тикет 02) и доказывает тестами, что по ключу действуют те же правила, что для менеджера. Новой логики сделок здесь нет: ключ и пользователь проходят через одни и те же функции.

Отметить «доступно ключу» и описать в OpenAPI (схема запроса, ответа и ошибок, выдуманный пример):

- `GET /api/v1/deals` (список с фильтрами эпиков `crm-deals` и `crm-fields`, курсор) и `GET /api/v1/deals/:id`.
- `POST /api/v1/deals` — создать: воронка, этап (по умолчанию первый), название, сумма и валюта, ответственный (по желанию), основной контакт — существующий по id или новый (имя, телефон, email), организация, `custom` по кодам. Правило «одна открытая сделка у человека в воронке» — 409 `OPEN_DEAL_EXISTS`; если конфликтующая сделка вне охвата ключа — ответ «чужой клиент» без её данных.
- `PATCH /api/v1/deals/:id` — название, сумма, валюта, ожидаемая дата закрытия, организация, `custom`. Этап, статус, ответственного и архив этот запрос не меняет.
- Смена этапа; смена ответственного (в том числе снять — сделка уходит в общую очередь); выиграть; проиграть с причиной (обязательна, не архивная, своего проекта); открыть заново; архивировать и вернуть из архива; перенести в другую воронку своего проекта (этап новой воронки, по умолчанию первый).

Ключу не открываются: удаление и восстановление, «взять в работу», допродажа, участники, строки товаров и «підставити суму», история и лента (решено без владельца — подтвердить; в решении владельца их нет, удаления через API нет по решению владельца). Эти маршруты отвечают ключу 403 `API_KEY_NOT_ALLOWED`.

Правила для ключа:

- Права и охват — по роли ключа (тикет 01): «сделки: смотреть / создавать / изменять» с охватом на чтение и изменение.
- Назначить, сменить или снять ответственного — только с правом «передача сделок» (`transfer_deals`), в том числе на сделке общей очереди (решено без владельца — подтвердить: у ключа нет «взять себе»). Ответственный — активный участник проекта; иначе 422.
- ADR 0003: изменение суммы не двигает, не выигрывает и не меняет этап; смена этапа не меняет статус и сумму; выигрыш не меняет этап. Каждое действие меняет ровно названные поля.
- Обязательные поля «всегда» и «с этапа X» проверяются той же функцией, что в канбане: смена этапа, выигрыш, создание сразу на этапе и перенос в воронку с пустым обязательным полем — 422 со списком полей в `errors` (формат тикета 02). Значения можно передать в том же запросе.
- Пользовательские поля — по коду, с правами роли ключа на группы полей: группа «только чтение» — 403 на запись, скрытая — 422 как неизвестный код; скрытые поля в ответе отсутствуют.
- Каждое изменение пишется в `change_log` с автором-ключом и в `audit_log` (тикет 01). `Idempotency-Key` и лимит запросов — тикет 02.
- Тикет не отправляет событий: их пишет тикет 05 в тех же функциях сделок.
- Из max-review тикета 01 (PR #28), учесть здесь:
  - значение «я» (`me`) в `filter=` для ключа сейчас молча превращается в NULL (`apps/api/src/filters/compile.ts`, `filters/custom.ts`), и «не я» даёт разные выборки для системного и пользовательского поля; `owner=me` уже отклоняется 400 (`apps/api/src/deals/board.ts`) — отклонять `me` в фильтре ключа так же;
  - `apps/api/src/fields/common.ts` (`entityReader`) читает `c.get('session').user.id` — маршрут, который его вызывает, при открытии ключу даст 500; перевести на автора запроса (`c.var.actor`);
  - обновление `last_used_at` держит блокировку строки ключа до конца запроса — при параллельных запросах одного ключа раз в минуту они ждут друг друга; решить, если станет заметно.

Проверка: нужна линза безопасности (`security`): права, охват и изоляция проекта для ключа.

Из тикета 05 (PR #30), учесть здесь:
- автор события для запроса по ключу проверен только прямым вызовом `requestAuthor`/`emitDealChanges` — добавить проверку `actor: {type: api_key}` в событии через настоящий HTTP-запрос по ключу;
- `apps/api/src/contacts/contacts.ts` (`contactContext`) берёт автора из `c.get('session').user.id` — при создании сделки с новым контактом по ключу нужен `requestAuthor(c.get('actor'))`, иначе `contact.created` не назовёт ключ автором.

## Результат

Ветка `crm-api/03`. Маршруты сделок, открытые ключу, объявлены через `keyRoute` в `apps/api/src/deals/openapi.ts` (схема запроса, ответ, пример) и обслуживают и ключ, и сессию теми же функциями `deals.ts`. Тесты — `apps/api/src/deals/api-key.test.ts`; помощник «запрос по ключу» для тикета 04 — `apps/api/src/testing/api-key.ts` (`createRole`, `createApiKey` → `key.api(method, path, { body })`).

Открыто ключу: `GET /deals`, `GET /deals/:id`, `POST /deals`, `PATCH /deals/:id`, `POST /deals/:id/{stage,owner,win,lose,reopen,archive,unarchive,move}`. Остальные маршруты сделок — 403 `API_KEY_NOT_ALLOWED`.

Решено без владельца — подтвердить (взят рекомендованный вариант тикета):

- Ключу не открыты удаление и восстановление, «взять в работу», допродажа, участники, строки товаров, «підставити суму», история и лента сделки.
- Назначить, сменить или снять ответственного ключом — только с правом «передача сделок», в том числе на сделке общей очереди. Новая сделка ключа без `ownerId` встаёт в общую очередь и права «передача сделок» не требует: это никого не назначает.
- Изменение полей ключом — новый `PATCH /api/v1/deals/:id` (название, сумма, валюта, ожидаемая дата закрытия, организация, `custom`). Прежний `PUT /api/v1/deals/:id` (все поля, в том числе ответственный и основной контакт) остаётся для `apps/web` и ключу закрыт. Смена ответственного — новый `POST /api/v1/deals/:id/owner` (`{ "ownerId": "…" | null }`), открыт и сессии.
- Ошибка схемы запроса на маршрутах сделок отвечает так же, как разбор тела до тикета, — 400 `INVALID_DEAL` с `details.path` и `errors[].field`, а не общим `INVALID_INPUT` тикета 02: код читает клиент `apps/web`. Тело с `Content-Type` не JSON — 415, неразбираемый JSON — 400 `INVALID_INPUT` (раньше — 400 `INVALID_DEAL`); оба случая — по коду @hono/zod-openapi, тестом не проверены.

Из max-review тикета 01 и тикета 05:

- «Я» (`me`) в `filter=` у ключа — 400 `INVALID_DEAL` (`readFilterParam(…, { me: false })`, как `owner=me`); построитель фильтра на «я» без пользователя бросает ошибку вместо молчаливого NULL.
- `entityReader` (`fields/common.ts`) и `contactContext` (`contacts/contacts.ts`) берут автора из `c.var.actor`: сделка с новым контактом по ключу пишет `contact.created` с автором-ключом (проверено настоящим HTTP-запросом).
- Блокировка строки ключа при обновлении `last_used_at` не тронута: заметной не стала, а `middleware/project-context.ts` вне тикета.

Заметки для тикета 04:

- Списки контактов и организаций читают `filter=` без `{ me: false }`: по ключу «я» в фильтре дойдёт до построителя и даст 500 — передать `me: ctx.actorId !== null`, как `deals/board.ts`.
- По коду: ключ с охватом контактов «свои» не создаст сделку с новым контактом — у такого контакта нет `created_by`, он вне охвата, ответ 404 `CONTACT_NOT_FOUND` (тестом не проверено).
