## Что сделать

Запросы сделок уже есть в эпике `crm-deals` (тикет 05) и работают по сессии. Тикет открывает ключу API ровно действия из решения владельца, описывает их в OpenAPI (тикет 02) и доказывает тестами, что по ключу действуют те же правила, что для менеджера. Новой логики сделок здесь нет: ключ и пользователь проходят через одни и те же функции.

Отметить «доступно ключу» и описать в OpenAPI (схема запроса, ответа и ошибок, выдуманный пример):

- `GET /api/v1/deals` (список с фильтрами эпиков `crm-deals` и `crm-fields`, курсор) и `GET /api/v1/deals/:id`.
- `POST /api/v1/deals` — создать: воронка, этап (по умолчанию первый), название, сумма и валюта, ответственный (по желанию), основной контакт — существующий по id или новый (имя, телефон, email), организация, `custom` по кодам. Правило «одна открытая сделка у человека в воронке» — 409 `OPEN_DEAL_EXISTS`; если конфликтующая сделка вне охвата ключа — ответ «чужой клиент» без её данных.
- `PATCH /api/v1/deals/:id` — название, сумма, валюта, ожидаемая дата закрытия, организация, `custom`. Этап, статус, ответственного и архив этот запрос не меняет.
- Смена этапа; смена ответственного (в том числе снять — сделка уходит в общую очередь); выиграть; проиграть с причиной (обязательна, не архивная, своего проекта); открыть заново; архивировать и вернуть из архива; перенести в другую воронку своего проекта (этап новой воронки, по умолчанию первый).

Ключу не открываются: удаление и восстановление, «взять в работу», допродажа, участники, строки товаров и «підставити суму», история и лента (решено без владельца — подтвердить; в решении владельца их нет, удаления через API нет по решению владельца). Эти маршруты отвечают ключу 403 `API_KEY_NOT_ALLOWED`.

Правила для ключа:

- Права и охват — по роли ключа (тикет 01): «сделки: смотреть / создавать / изменять» с охватом на чтение и изменение.
- Назначить, сменить или снять ответственного — только с правом «передача сделок» (`transfer_deals`), в том числе на сделке общей очереди (решено без владельца — подтвердить: у ключа нет «взять себе»). Ответственный — активный участник проекта; иначе 422.
- ADR 0003: изменение суммы не двигает, не выигрывает и не меняет этап; смена этапа не меняет статус и сумму; выигрыш не меняет этап. Каждое действие меняет ровно названные поля.
- Обязательные поля «всегда» и «с этапа X» проверяются той же функцией, что в канбане: смена этапа, выигрыш, создание сразу на этапе и перенос в воронку с пустым обязательным полем — 422 со списком полей в `errors` (формат тикета 02). Значения можно передать в том же запросе.
- Пользовательские поля — по коду, с правами роли ключа на группы полей: группа «только чтение» — 403 на запись, скрытая — 422 как неизвестный код; скрытые поля в ответе отсутствуют.
- Каждое изменение пишется в `change_log` с автором-ключом и в `audit_log` (тикет 01). `Idempotency-Key` и лимит запросов — тикет 02.
- Тикет не отправляет событий: их пишет тикет 05 в тех же функциях сделок.

Проверка: нужна линза безопасности (`security`): права, охват и изоляция проекта для ключа.
