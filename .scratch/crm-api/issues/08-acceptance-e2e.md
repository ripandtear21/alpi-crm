# Приёмка: тестовый приёмник получает подписанные события и двигает сделку ключом без зацикливания

Type: task
Status: open
Blocked by: 03, 04, 06, 07
Source: .scratch/crm-build/issues/03-automation-api-contract.md (Answer: «Тикеты», волна 4); .scratch/crm-api/spec.md («Приёмка владельцем»); docs/research/webhook-delivery.md на ветке origin/research/webhook-delivery, разделы 1.3, 3.3; .scratch/crm-deals/issues/16-acceptance-e2e.md

## Что сделать

Сквозной автотест сценария приёмки из `spec.md` эпика. Настоящие API и обработчик фоновых задач на embedded PostgreSQL с данными `pnpm seed`; тестовый приёмник событий — HTTP-сервер внутри теста на `localhost` (разрешён переменной окружения тикета 06 только в тестовом запуске), паузы повторов pg-boss укорочены настройкой теста.

Приёмник ведёт себя как внешняя автоматизация владельца:

- проверяет подпись каждого события пакетом `standardwebhooks` (`verify()`), неверную отклоняет;
- запоминает обработанные `webhook-id` и повтор пропускает;
- пропускает событие, у которого `actor` — его собственный ключ;
- на `deal.created` с автором-пользователем переводит сделку на следующий этап запросом `/api/v1` своим ключом, с `Idempotency-Key`.

Шаги:

1. Администратор ALPI (сессия) создаёт ключ «Автоматизація (тест)» с ролью, где есть «сделки: смотреть, изменять» и «передача сделок»; секрет показан один раз.
2. Администратор создаёт адрес приёмника с подпиской на `deal.created`, `deal.stage_changed`, `deal.won`; получает секрет `whsec_…`.
3. Менеджер создаёт сделку. Приёмник получает `deal.created` с `actor.type = user`, подпись сходится.
4. Приёмник переводит сделку ключом на следующий этап. CRM отвечает 200; приходит `deal.stage_changed` с `actor` = ключ приёмника; приёмник его пропускает. Через время ожидания: приёмник сделал ровно один запрос, этап сделки сменился ровно один раз — цикла нет.
5. Приёмник отвечает 500 на следующее событие один раз: событие приходит повторно с тем же `webhook-id`, приёмник обрабатывает его один раз; в журнале доставок две попытки.
6. Ручной повтор доставки из журнала (запрос тикета 06) доставляет событие ещё раз с тем же `webhook-id`; приёмник узнаёт дубль.
7. Сумму сделки меняют ключом: этап и статус не изменились, события `deal.stage_changed` и `deal.won` нет (ADR 0003).
8. Приёмник отвечает 410: адрес отключён, у администратора — предупреждение.
9. Ключ отозван: следующий запрос приёмника — 401.

Короткий прогон экранов на Playwright в наборе `pnpm e2e` эпика `crm-deals`: создание ключа и показ секрета один раз (шаг 1), создание адреса (шаг 2), журнал доставок с повтором (шаги 5–6), отключённый адрес с причиной (шаг 8). Тест создаёт свою базу и не зависит от порядка запусков; задание CI (`.github/workflows/ci.yml`) уже есть — новые шаги идут в нём, при падении сохраняются трассировка и снимки.

В тесте — только выдуманные данные. Тикет не меняет поведения приложения; найденные расхождения чинятся в тикете, которому принадлежит часть, или здесь, если правка мелкая.
