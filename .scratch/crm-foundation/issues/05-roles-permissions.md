## Что сделать

По решению тикета карты «Роли, права и видимость» (`.scratch/crm-mvp/issues/07-roles-and-visibility.md`): роли проекта; права — матрица «часть системы × действие (смотреть, создавать, изменять, удалять)» + отдельные права (выгрузка, массовые операции, передача сделок, настройки проекта, пользователи и роли) + охват (свои / команды / все) для сделок, контактов, задач, платежей; место под права на группы полей. Четыре шаблона ролей создаются вместе с проектом. Защиты: роль «администратор» нельзя удалить или урезать; в проекте всегда ≥ 1 администратор. Одна роль у пользователя в проекте. `requirePermission(resource, action)` для API и функция охвата для запросов. Экран редактора ролей (таблица галочек).

## Where in code

packages/db/migrations/**, packages/shared/src/permissions.ts, apps/api/src/roles/**, apps/api/src/middleware/permissions.ts, apps/web/src/routes/ (настройки → роли).

## Решения без владельца — подтвердить

- Право «пользователи и роли» не даёт захватить проект (после проверки REJECTED, правила в `apps/api/src/roles/guard.ts`): (а) роль администратора назначает, а роль участника-администратора меняет только администратор проекта; (б) не-администратор при создании, изменении и назначении роли не выдаёт прав сверх своих — действий, охвата, отдельных прав; проверяется только добавляемое, уже имеющиеся у роли права можно оставить или убрать; (в) не-администратор не меняет свою роль участника и не правит роль, назначенную ему. Проверка в коде API, а не в триггере: правила зависят от того, кто меняет, а база этого не знает.

## Результат

- Миграция `packages/db/migrations/0004_roles.ts`: таблица `role` (по проекту, RLS), права роли — JSONB, проверяемый по каталогу `packages/shared/src/permissions.ts`: 12 частей системы × смотреть / создавать / изменять / удалять, отдельные права (выгрузка, массовые операции, передача сделок, настройки проекта), охват «свои / команда / все» отдельно для чтения и изменения у сделок, контактов, задач и платежей, место под права на группы полей (пока только пустое). `project_member.role_id` обязателен; прежние участники получили роль администратора.
- База держит правила, не зависящие от пользователя: четыре шаблона (администратор, руководитель, тимлид, менеджер) создаёт триггер на вставку проекта; роль администратора нельзя удалить, изменить или перенести её признак; у последнего администратора нельзя снять роль (блокировка против одновременных снятий; полагается на READ COMMITTED). У роли приложения отозвано изменение `"user".role`.
- API: `requirePermission(resource, action)` (`apps/api/src/middleware/permissions.ts`) после проверки участия, 403 `PERMISSION_DENIED`; функции охвата (`apps/api/src/roles/scope.ts`), команды подключит тикет 06 через `TeamResolver`. Маршруты ролей и назначения роли участнику (`apps/api/src/roles/roles.ts`) проходят через `apps/api/src/roles/guard.ts`: роль администратора назначает и снимает только администратор; не-администратор не выдаёт прав сверх своих (при создании, изменении и назначении) и не трогает свою роль. Предел тела запроса — 100 КБ на весь API.
- Клиент: настройки → роли (`apps/web/src/routes/settings/`), таблица галочек, охват, роль администратора только для чтения, uk и ru; на 375 px таблица прокручивается по горизонтали.
- 139 тестов. Проверка: первый раунд REJECTED (держатель права «пользователи и роли» мог назначить себе роль администратора и выдавать права шире своих), второй — VERIFIED. Gate full зелёный.

- `middleware/permissions.ts:28` — права действующего пользователя читаются без блокировки строки участия; узкое окно, выйти за прежние права нельзя.
