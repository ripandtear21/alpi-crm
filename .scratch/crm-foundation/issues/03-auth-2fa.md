# Вход: email и пароль, обязательная двухфакторная аутентификация

Type: task
Status: done 2026-11-04T01:11Z
Blocked by: 02
Source: .scratch/crm-mvp/spec.md, раздел 12, эпик 1

## Что сделать

Подключить Better Auth (последний патч 1.7.x) к PostgreSQL через Kysely-адаптер: без открытой регистрации (пользователей создаёт администратор), вход по email и паролю, плагин twoFactor (TOTP, резервные коды) — пока пользователь не включил 2FA, API отвечает 403 на всё, кроме настройки 2FA и выхода. Сессии в базе, cookie HttpOnly. Ограничение частоты попыток входа (хранилище — база). Плагин admin: бан, отзыв сессий. Первый пользователь-владелец системы создаётся CLI-скриптом. Экраны клиента: вход, ввод кода 2FA, настройка 2FA (QR).

## Where in code

apps/api/src/auth/**, apps/api/src/index.ts, packages/db/migrations/** (таблицы Better Auth), apps/web/src/routes/ (экраны входа), scripts/create-owner.ts.

## Результат

- Better Auth 1.7.15 (1.7.16 вышел меньше суток назад, политика pnpm `minimumReleaseAge` его не пускает) на PostgreSQL через Kysely. Таблицы Better Auth — миграция `packages/db/migrations/0002_auth.ts`, глобальные (пользователи общие для проектов, ADR 0001), в snake_case; внешний ключ `project_member.user_id → user`.
- Регистрации нет: пользователей заводит администратор (плагин admin: бан, отзыв сессий). Пароль от 12 символов. Лимит входа — 5 попыток в минуту с адреса, счётчики в базе; адрес клиента с учётом `TRUSTED_PROXIES`.
- 2FA обязательна: без включённой 2FA API отвечает 403 на всё, кроме настройки 2FA, выхода и чтения сессии (`apps/api/src/auth/access-guard.ts`). Сессия получает отметку «второй фактор пройден» только после кода; при включённой 2FA охрана пускает только такие сессии; включение 2FA удаляет все сессии пользователя. «Запомнить устройство» отключено.
- База: API подключается отдельной ролью входа (член `alpi_app`, без SUPERUSER и BYPASSRLS), миграции — служебной ролью из `MIGRATION_DATABASE_URL`; мигратор создаёт и обновляет роль входа API (`packages/db/src/app-role.ts`). API не стартует, если его роль слишком сильная. В docker-compose — разовая служба `migrate` перед `api`.
- Владелец системы создаётся `pnpm create-owner <email> [имя]` (`apps/api/src/cli/create-owner.ts`), пароль — со stdin без эха или из `OWNER_PASSWORD`, в вывод не попадает.
- Клиент: экраны входа, ввода кода (TOTP или резервный код), настройки 2FA с QR (`uqr`), uk и ru; защита маршрутов в `apps/web/src/router.tsx`.
- 79 тестов, интеграционные — на embedded PostgreSQL. Проверка: первый раунд REJECTED (сессия, открытая по паролю до включения 2FA, после включения получала полный доступ; API ходил в базу суперпользователем), второй раунд VERIFIED. Gate full зелёный.

- `apps/api/src/auth/auth.ts:103` — наследование отметки второго фактора при смене пароля без теста.

- Кнопки «Выйти» в шапке нет (только на экране настройки 2FA). В compose нет готовой команды для `create-owner`. Docker на машине нет — службу `migrate` в контейнерах не запускали.
