# Unitalk как телефония для нашей CRM

Дата исследования: 2026-11-04. Источники — официальная документация API Unitalk, база знаний
unitalk.cloud, страница тарифов и публичная инструкция Unitalk по обработке событий (Google Doc,
ссылка из документации API). В личный кабинет не входили, аккаунтов не создавали.

Метки: **факт** — прочитано в первоисточнике или проверено запросом; **вывод** — следует из
фактов, но напрямую не проверено.

## Кратко

- У Unitalk есть REST API: `https://api.unitalk.cloud/api`, все методы — POST, ключ в заголовке
  `Authorization` (можно `Bearer <ключ>`). Ключ даёт полный доступ к проекту, областей прав нет
  (**факт**).
- События звонков приходят вебхуками на любой внешний адрес: начало, перенаправление, ответ,
  завершение звонка. На одно событие можно повесить до 5 обработчиков (**факт**). Значит, события
  может получать и наша CRM, и внешняя автоматизация владельца, каждая на свой адрес (**вывод**).
- Подписи вебхуков нет. Можно добавить свои заголовки (до 10) и параметры адреса (до 20) — так
  передаётся секрет (**факт**). Повторы при ошибке доставки в документации не описаны.
- Для ночной сверки есть история звонков `/history/get`: период, фильтры, до 1000 записей на
  страницу, смещение `offset` (**факт**).
- В каждом звонке есть ссылка на запись `link` (только у отвеченных). Unitalk хранит записи, пока
  проект активен, объём ограничен минутами записи по тарифу (**факт**).
- Есть маршрутизация «к ответственному менеджеру» с режимом «Запрос к вашему API»: при входящем
  звонке Unitalk спрашивает наш адрес, кому отдать звонок, мы отвечаем номером линии (**факт**).
  Таймаут и поведение при отказе нашего сервера не описаны.
- Сотрудников даёт `/users/list`: email, имя, внутренняя линия, телефон, id (**факт**). Сопоставлять
  с пользователями CRM удобно по email, а звонки — по внутренней линии.
- API и вебхуки есть только на тарифах Medium и Max. Звонки через API (`/calls/originateNew`) —
  только Max. Звонок из CRM на линию менеджера (`/phones/directCall`) — в разделе API, к какому
  тарифу относится, неясно (**факт** по таблице тарифов, детали — **не проверено**).
- Готовых интеграций с n8n, Make и Zapier у Unitalk нет. Есть ApiX-Drive (**факт** по сайту
  Unitalk и каталогам). Для внешней автоматизации остаются прямые вебхуки Unitalk.

## API и авторизация

Источник: https://unitalk.cloud/api-references/ (есть версии UA и RU).

- **Базовый адрес:** `https://api.unitalk.cloud/api`; пути методов задаются относительно него
  (**факт**).
- **Метод:** все запросы — POST. Тело чаще JSON, у некоторых методов параметры в адресе или
  `application/x-www-form-urlencoded` (**факт**).
- **Авторизация:** ключ (токен) создаётся в личном кабинете на странице «API»
  (`https://my.unitalk.cloud/index.html#api`, в интерфейсе — раздел «Интеграции → API»). Ключ
  передаётся в каждом запросе в заголовке `Authorization`, допускается формат `Bearer <ключ>`.
  Цитата: ключ даёт доступ к проекту «with maximum privileges». Областей прав (scopes) нет
  (**факт**). Ошибка авторизации: `{"status": "Error", "message": "Authorization invalid"}`.
  Запрос без ключа к `/history/get` возвращает HTTP 200 с телом ошибки (**факт**, проверено
  запросом): статус ответа надо определять по полю `status`, а не по коду HTTP.
- **Версии:** версионирования нет (**факт**: в документации не упомянуто).
- **Ограничения частоты:**
  - больше 30 запросов за 10 секунд — временная блокировка, повторное превышение — блокировка
    дольше;
  - больше 100 запросов за 10 секунд — постоянная блокировка;
  - не больше 20 одновременных запросов и 15 запросов в секунду (**факт**).
- **Учёт запросов:** запросы входят в квоту тарифа, а «стоимость» запроса зависит от времени
  обработки: до 50 мс — 1 запрос, до 200 мс — 2, до 500 мс — 3, до 1000 мс — 4, дольше — 5
  (**факт**). Остаток виден в кабинете в разделе «Мой тариф».

## События звонков (вебхуки)

Источники: раздел «Webhooks» документации API и «Инструкция по обработке событий»
(https://docs.google.com/document/d/17hqVTVDxvdPKH-71RDg399laQJ9Q9NVI75apjYiNUz0/edit).

**Как настраивается (факт).** В кабинете на странице «Обработка событий» создаётся действие
«Отправить вебхук». Затем на странице «API» это действие назначается на события звонков. В
действии задаются:

- адрес, на который отправлять;
- HTTP-метод: POST, GET, PUT, DELETE или PATCH;
- заголовки, до 10 (документация прямо предлагает так передавать `Authorization`);
- параметры адреса, до 20, в значения можно подставлять динамические значения вида
  `{{PHONE_NUMBER}}`;
- тело: «Стандартный JSON», «Указанный JSON» (свой шаблон с динамическими значениями), форма
  (urlencoded) или пустое тело.

Действие назначается на событие независимо от того, через какую внешнюю линию идёт звонок. На одно
событие — не больше 5 обработчиков (**факт**). Так же подключает Unitalk, например, KeyCRM: её
администратор создаёт вебхук со «Стандартным JSON» методом POST и назначает его на события звонков
(https://help.keycrm.app/en/communications-sms-email-instagram-telegram-viber-marketplace-chats-telephony/how-to-connect-uni-talk-nextel-phone-service-for-administrators).

**События звонков (факт):** «Начало звонка» (`CALL_NEW`), «Перенаправление звонка»
(`CALL_REDIRECT`), «Ответ на звонок» (`CALL_ANSWER`), «Завершение звонка» (`CALL_END`). Отдельного
события «пропущенный» нет. Пропущенный звонок — это `CALL_END` с `state` не `ANSWER`, например
`NOANSWER` или `BUSY` (**вывод**).

**Стандартный JSON для событий звонков (факт):**

```json
{
  "event": "CALL_END",
  "call": {
    "id": 1091944,
    "dbid": 275,
    "from": "380505557182",
    "to": ["2000"],
    "lastGroupName": "Sales managers",
    "outerNumber": "site.ua",
    "direction": "IN",
    "date": "2018-07-09 16:58:52",
    "secondsFullTime": 19,
    "secondsTalk": 9,
    "utmSource": "google", "utmMedium": "search", "utmCampaign": "web",
    "utmTerm": "...", "utmContent": "content",
    "googleId": "...", "facebookClientId": "...", "referer": "google.com",
    "callback": true,
    "comment": "...",
    "state": "ANSWER",
    "source": "REGULAR",
    "link": "https://api.unitalk.cloud:8443/tracking/rec/1531144732.920/2018-07-09",
    "meta": "some info",
    "cause": 16
  }
}
```

Что важно в полях:

- `id` — случайный идентификатор, общий для всех событий одного звонка. `dbid` — идентификатор
  звонка в базе проекта, под ним звонок потом лежит в истории (**факт**). Ключ для склейки событий
  в CRM — `id`, для сверки с историей — `dbid` (**вывод**: история тоже отдаёт оба поля).
- `direction`: `IN`, `OUT`, `INNER` (внутренний).
- `to` — номера, на которые ушёл звонок: на `CALL_NEW` входящего — пусто, на `CALL_REDIRECT` — один
  или несколько, на `CALL_ANSWER` — один номер, на `CALL_END` — пусто или номера операторов,
  принявших звонок (**факт**). **Идентификатора сотрудника в событии нет** — только номер
  внутренней линии (или мобильного). Менеджера определяем по линии через `/users/list` (**вывод**).
- `secondsFullTime`, `secondsTalk` известны только в `CALL_END`.
- `state` (на `CALL_NEW` и `CALL_REDIRECT` — `null`): `ANSWER`, `BUSY`, `FAIL`, `NOANSWER`,
  `CHANUNAVAIL`, `NOMONEY`, `BUSYOUT`, `WRONGDIR`, `BLOCKED`, `DIALING`, `UNREACHABLE`, `NOT_EXIST`.
- `source`: `REGULAR`, `TRACKING`, `CLICK2CALL`, `LEAD_CATCHER`, `FORM`, `CALLBACK`, `AUTO_CB`
  (автоперезвон на пропущенный), `AUTODIAL`, `API_CALL`, `C2C_API`.
- `link` — ссылка на запись, есть только при `state = ANSWER`.
- `meta` — строка до 1000 символов, которую можно передать при запуске звонка через API; пригодна,
  чтобы связать звонок из CRM со сделкой.
- Даты — строкой `yyyy-MM-dd HH:mm:ss` без часового пояса (**факт**). Пояс, видимо, — пояс проекта
  (**не проверено**).

**Подпись и повторы.** Подписи (HMAC и т. п.) нет: в документации о ней ничего (**факт**). Защита —
секрет в своём заголовке или параметре адреса (**вывод**). Повторы при ошибке доставки, таймаут
ожидания ответа и порядок доставки событий **не описаны**. CRM должна принимать события
повторно и не по порядку и не полагаться на доставку: нужна ночная сверка по истории (**вывод**).

**Кроме звонков** есть вебхук «Движение баланса» (адрес задаётся на странице «API»), события
голосовых меню, автообзвонов и голосовой очереди (**факт**). Есть и входящие вебхуки Unitalk, но
только для добавления и удаления номеров в автообзвоне (**факт**).

## История звонков

Источник: раздел «Call history» документации API.

- **Метод:** `POST /history/get`, JSON (**факт**).
- **Параметры:** `dateFrom`, `dateTo` в формате `yyyy-MM-dd HH:mm:ss` (обязательны), `limit` от 1 до
  1000 (обязателен), `offset` — смещение (**факт**).
- **Фильтры** (`filter`): `direction` (`IN`/`OUT`/`INNER`), `minDuration`, `calledFrom` и
  `calledTo` (части номеров), `outerNum`, `exactPhone`, `newLead` (первый звонок с номера),
  `answered`, `lost` (пропущенный и не перезвоненный), `voiceMessage` (**факт**).
- **Порядок:** по убыванию `id`. Ответ содержит `count` — общее число звонков по условиям (**факт**).
  Страницы по смещению при убывающем порядке могут «съезжать», если звонки добавляются во время
  выгрузки. Для ночной сверки закрытых суток это не страшно (**вывод**).
- **Поля звонка:** `id`, `dbid`, `date`, `source`, `direction`, `from`, `to[]`, `lastGroupName`,
  `secondsFullTime`, `secondsTalk`, `link`, `comment`, `state`, `cause`, `callback`, UTM-метки,
  `outerNumber`, `holdTime`, `pcpTime`, `googleId`, `facebookClientId`, `referer` (**факт**). Набор
  почти совпадает с вебхуком, поля `meta` в примере истории нет.
- Звонки, созданные `/calls/originateNew` (информационные), в историю не попадают (**факт**).
- Стоимость сверки: один запрос на 1000 звонков; при медленном ответе он считается за 5 запросов
  квоты (**вывод** из правил учёта).
- Есть ещё `/operator/statistic` — статистика по операторам за период (**факт**), для сверки не
  нужна.

## Записи

- **Где взять:** поле `link` в вебхуке `CALL_END` и в истории звонков, только для отвеченных
  (**факт**). Пример ссылки в документации:
  `https://api.unitalk.cloud:8443/tracking/rec/1531144732.920/2018-07-09`.
- **Доступ к ссылке:** запрос по примерной ссылке без ключа вернул HTTP 200 с телом
  `{"status":"Error","message":"Access denied"}` (**факт**, проверено запросом). Нужен ли для
  скачивания ключ API в заголовке, или ссылка из реального звонка открывается без него, — **не
  проверено**.
- **Сертификат:** порт 8443 на `api.unitalk.cloud` отдаёт сертификат на имя
  `cstat.nextel.com.ua` (Let's Encrypt), а не на `api.unitalk.cloud` (**факт**, проверено
  `openssl s_client`). Клиент со строгой проверкой TLS (Node `fetch`, curl по умолчанию) скачать по
  такой ссылке не сможет. Возможно, в настоящих ссылках другой домен — **не проверено**. Отключать
  проверку сертификата нельзя; решение — выяснить у поддержки или взять ссылку из реального звонка.
- **Формат файла:** в документации не указан (**не проверено**). Вероятно, MP3 (**вывод**, не
  подтверждён).
- **Время жизни ссылки:** не описано. Ссылка выглядит постоянной (идентификатор записи и дата), а не
  временной подписанной (**вывод**).
- **Хранение у Unitalk:** записи хранятся, пока клиент пользуется сервисом. Удаляются вместе с
  проектом, если сервисом не пользуются больше 2 месяцев и на счёте меньше 100 единиц валюты
  (**факт**, FAQ https://unitalk.cloud/services/recording-telephone-conversations/). Объём записи
  ограничен квотой минут по тарифу, сверх неё — докупается (**факт**, таблица тарифов). Что
  происходит со старыми записями при исчерпании квоты — **не проверено**.
- **Выгрузка во внешнее хранилище:** на Medium и Max есть «хранение записей на своих серверах» —
  экспорт в AWS S3, Google Drive или на свой HTTP-сервер (**факт**, https://unitalk.cloud/prices/).
  Как это настраивается и что приходит на HTTP-сервер — **не проверено** (в API-документации не
  описано). Это запасной путь, если скачивание по `link` не заработает.
- **Голосовая аналитика:** `/calls/analytics/create` строит расшифровку, но только для звонков, у
  которых сохранены раздельные дорожки (**факт**). Не для MVP.

## Маршрутизация

**«Перевод к ответственному менеджеру» с запросом к нашему API (факт).** Во входящем сценарии
(«Звонки → Настройки → Входящие сценарии») выбирается шаг «К ответственному менеджеру» и включается
опция «Запрос к Вашему API» с адресом. При выполнении шага Unitalk шлёт POST:

```json
{ "event": "ROUTE", "call": { "from": "380505557182", "outerNumber": "380442949168" } }
```

Ответ нашего сервиса:

```json
{ "operatorNumber": "2048", "callerName": "Александр", "ivrId": 487 }
```

- `operatorNumber` — внутренняя линия (SIP) или мобильный номер ответственного, может быть `null`;
- `callerName` — имя звонящего, которое покажет SIP-клиент менеджера;
- `ivrId` — голосовое меню для звонящего, может быть `null`.

Проверять, свободен ли менеджер, не нужно: если он занят, звонок ему не уйдёт (**факт**). Куда
звонок пойдёт тогда — по следующему шагу сценария (**вывод**: сценарий — цепочка шагов с
ожиданием, пример из базы знаний: «ответственный 15 секунд → отдел 15 секунд → руководитель»,
https://unitalk.cloud/knowledge-base-articles/incoming-calls-scripts-setup/).

**Таймаут и отказ.** Сколько Unitalk ждёт ответа, что делает при ошибке, неверном JSON или
`operatorNumber = null`, есть ли подпись или секрет у этого запроса — **не описано**. Можно ли
добавить к этому запросу свой заголовок — тоже неясно; в документации задаётся только адрес. Секрет
придётся передать в самом адресе (**вывод**). Сервис должен отвечать быстро — из кэша, без
внешних вызовов (**вывод**).

**Как это стыкуется с ADR 0003** (CRM сама не меняет сделки; автоматика — внешняя, через API и
события; запрос телефонии «кому направить звонок» CRM обслуживает сама):

- Ответ на `ROUTE` — чтение, сделку он не меняет. CRM находит контакт по номеру `from` и отвечает
  линией ответственного по открытой сделке. Это укладывается в решение (**вывод**).
- Unitalk умеет отправлять события звонков на любой внешний адрес, до 5 обработчиков на событие
  (**факт**). Поэтому есть два равноправных варианта: (а) Unitalk шлёт события и в CRM, и сразу во
  внешнюю автоматизацию владельца; (б) Unitalk шлёт только в CRM, а CRM пересылает своё событие
  «звонок состоялся или пропущен» в автоматизацию. Вариант (б) даёт автоматизации уже
  сопоставленные контакт, сделку и менеджера (**вывод**).
- Если адрес ответственного не нашёлся, у других интеграций Unitalk есть «ответственный по
  умолчанию» по дням недели. Для `ROUTE` аналог — вернуть `null` и отдать звонок следующему шагу
  сценария (**вывод**).

**Готовые конструкторы автоматизаций.** Готовых интеграций Unitalk с n8n, Make и Zapier не найдено.
На сайте Unitalk среди интеграций их нет. Страницы `zapier.com/apps/unitalk` и
`n8n.io/integrations/unitalk` отвечают 404; страница Make ответила 403 (защита от роботов) —
наличие там приложения **не проверено**. Есть коннектор ApiX-Drive
(https://apix-drive.com/ru/nextel-api,
https://unitalk.cloud/knowledge-base-articles/possibilities-of-integrating-unitalk-with-apix-drive/).
Через стандартный вебхук-узел n8n/Make/Zapier события Unitalk принимаются и без готовой
интеграции (**вывод**).

**Прочее (факт):** голосовая очередь может спросить наш адрес о приоритете звонка (ответ
`setPriority` от 1 до 10). Это не для MVP.

## Сотрудники

- `POST /users/list`, пустое тело: `email`, `firstName`, `lastName`, `middleName`, `phone`, `line`
  (внутренний номер АТС), `role`, `id`, `workStatus`, `workStatusName` (**факт**).
- `POST /phones/inner` — словарь «внутренняя линия → `online`/`busy`/`offline`» (**факт**).
- `POST /groups/action` с `{"action":"GET"}` — отделы и их номера с именами (**факт**).
- `POST /dictionary?type=INNER_PHONE` и `type=USER` — справочники «линия → имя оператора» и «id →
  имя пользователя» (**факт**).
- `POST /users/getStatus`, `/phones/inner/setStatus`, `/users/workHistory` — рабочие статусы
  (**факт**).

Сопоставление: пользователь CRM ↔ пользователь Unitalk по `email`; в CRM хранится `line` и `id`
пользователя Unitalk. События и история дают только номер линии в `to`, поэтому ключ для звонков —
`line` (**вывод**). Если менеджер принял звонок на мобильный (`phone`), в `to` будет мобильный —
сопоставлять нужно и по нему (**вывод**).

## Звонок из CRM (не MVP)

- `POST /phones/directCall` (form-urlencoded: `sip`, `number`, `meta`): сначала звонит SIP-клиент
  менеджера, после ответа — клиенту. Документация прямо пишет, что так обычно делают в CRM
  (**факт**). Ошибка `Sip not ready` — линия офлайн или занята.
- `POST /calls/originateC2c` — звонок клиенту с цепочкой шагов на линию, мобильный или отдел
  (**факт**). Такой звонок «не виден в CRM-системах», но есть в истории и вебхуках.
- `POST /calls/hangup` — завершить звонок по `id` из вебхука (**факт**).
- Уведомления в браузерном расширении Web Dialer: `/widget/sendNotification` показывает менеджеру
  карточку со ссылками на контакт и сделку в нашей CRM (**факт**). Удобно для всплывающей карточки
  без своего софтфона, не MVP.

## Интеграции

- **Pipedrive (факт):** встроенная интеграция в кабинете Unitalk, не приложение из Marketplace
  Pipedrive. Подключается доменом компании и личным API-ключом Pipedrive
  (https://unitalk.cloud/knowledge-base-articles/instructions-for-connecting-and-setting-up-unitalk-and-pipedrive-integration/).
  Что делает: создаёт контакты, сделки или лиды при звонках (в том числе исходящих — по
  переключателю), к созданным сущностям ставит задачи с информацией о звонке. Есть
  «ответственный по умолчанию» для пропущенных звонков по дням недели и таблица «пользователь
  Pipedrive → внутренняя линия» для звонков из карточки. Прикрепляется ли запись к Pipedrive — в
  статье не сказано.
- **Связь с нашим Pipedrive (вывод):** в Marketplace нашего Pipedrive установлены Ringostat и
  Zapier (docs/research/our-pipedrive.md). Интеграция Unitalk там видна не будет, потому что она
  работает по API-ключу. Задачи «Входящий/Исходящий/Пропущенный звонок» могут создаваться уже
  Unitalk. Правило «Дзвінок → відповідальний = власник угоди» — автоматизация Pipedrive; аналог в
  Unitalk — шаг «к ответственному» во входящем сценарии. Какой сценарий включён сейчас — **не
  проверено**.
- **Другие CRM (факт), что показывают:**
  - Bitrix24: звонки в карточках клиента и сделки, записи можно прослушать; ответственный — тот, кто
    принял звонок; перевод входящего на ответственного по карточке; имя «клиент — ответственный» в
    SIP-клиенте; ссылки на контакт и сделку в истории звонков Unitalk
    (https://unitalk.cloud/knowledge-base-articles/integration-of-bitrix24-with-ip-telephony/).
  - HubSpot: создание контактов и сделок, «только по отвеченным», отправка звонков в CRM,
    соответствие статусов звонка, ответственные за пропущенные, воронки
    (https://unitalk.cloud/knowledge-base-articles/configuring-unitalk-ip-telephony-integration-with-hubspot-crm/).
  - KeyCRM: вся история звонков с записями, маршрут к закреплённому менеджеру, сопоставление линий
    с пользователями; подключается ключом API и вебхуком Unitalk — то же, что нужно нам.
  - Всего на сайте «50+» интеграций: Zoho, Odoo, SalesDrive, OneBox, Creatio, amoCRM/Kommo,
    RetailCRM, Salesforce, Dynamics 365, Zendesk и другие
    (https://unitalk.cloud/services/integration/).
- **Ожидания для нашей CRM (вывод):** минимум, который даёт любая интеграция Unitalk, — звонок в
  карточке контакта и сделки с записью, создание контакта или сделки по новому номеру (в нашем
  случае это делает внешняя автоматизация, ADR 0003), ответственный за пропущенные, маршрут к
  ответственному, звонок из карточки.

## Что не удалось проверить

Нужны доступ к кабинету Unitalk (роль администратора) или ответ поддержки
(Telegram-бот https://t.me/unitalk_cloud_bot):

1. Тариф школы и его квоты: запросы API, вебхуки, минуты записи. Есть ли API и вебхуки (нужен
   Medium или выше).
2. Как сейчас подключён Pipedrive: включена ли встроенная интеграция Unitalk → Pipedrive, какие
   сущности она создаёт, кто «ответственный по умолчанию».
3. Входящие сценарии: используется ли шаг «к ответственному менеджеру», с каким источником
   (Pipedrive или «Запрос к Вашему API»), какие шаги стоят следом.
4. Уже настроенные обработчики событий и вебхуки (их не больше 5 на событие — нужно знать, сколько
   мест занято).
5. Повторы вебхуков: есть ли повтор при ошибке, таймаут ответа, порядок доставки.
6. Таймаут запроса `ROUTE` и поведение при ошибке или `null`; можно ли добавить свой заголовок.
7. Записи: нужен ли ключ API для скачивания по `link`; домен настоящих ссылок (сертификат на
   `api.unitalk.cloud:8443` выписан на `cstat.nextel.com.ua`); формат файла; живёт ли ссылка
   бессрочно; что будет при исчерпании квоты минут.
8. Настройка экспорта записей на свой HTTP-сервер: что и в каком виде приходит.
9. Часовой пояс дат в вебхуках и истории.
10. Входит ли `/phones/directCall` в тарифную опцию «звонки через API».
11. Есть ли приложение Unitalk в Make (страница вернула 403).
12. Тестовый ключ или тестовый проект для разработки: пробный период — 14 дней, но аккаунт мы не
    создавали.
