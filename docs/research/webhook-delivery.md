# Надёжная доставка исходящих событий (вебхуков): как принято делать

Дата исследования: 2026-11-04. Отвечает на тикет
[«Надёжная доставка событий: как принято делать»](../../.scratch/crm-build/issues/04-webhook-delivery-research.md).
Контекст — [ADR 0003](../adr/0003-crm-ne-menyaet-sdelki-sama.md): CRM сама сделки не меняет,
внешняя автоматизация владельца (n8n, Make, свой сервис) получает события вебхуками и вызывает
наш REST API.

Источники — спецификация Standard Webhooks, документация Stripe, GitHub, Svix, pg-boss, PostgreSQL,
n8n и Make, исходный код библиотек на GitHub и реестр npm. Нигде не входили, аккаунтов не создавали.

Метки: **факт** — прочитано в первоисточнике или проверено запросом; **вывод** — следует из
фактов, но напрямую не проверено.

## Кратко: рекомендация

1. **Таблица событий + задача pg-boss в той же транзакции.** Изменение сделки, строка в нашей
   таблице `webhook_events` и задача pg-boss пишутся одной транзакцией Kysely: у pg-boss есть
   адаптер `fromKysely(trx)` (**факт**). Отдельный опрашивающий процесс (poller) и LISTEN/NOTIFY
   самим писать не нужно: pg-boss сам опрашивает очередь и по желанию будит рабочих через NOTIFY
   (**факт**). Таблица pg-boss — очередь, наша таблица — журнал событий и доставок (**вывод**).
2. **Доставка «хотя бы один раз» (at-least-once), порядок не обещаем.** Так делают Stripe и
   Standard Webhooks; Make по умолчанию сам обрабатывает входящие вебхуки параллельно, то есть
   порядок всё равно теряется на стороне приёмника (**факт**). Приёмник отбрасывает повторы по
   заголовку `webhook-id` (**факт**, рекомендация спецификации). Строгий порядок по сделке можно
   включить позже политикой очереди pg-boss `key_strict_fifo` (**факт**), но у неё есть цена
   (раздел 1.4).
3. **Повторы ~3 суток с растущей паузой.** Stripe — до 3 суток, Standard Webhooks — 10 попыток
   за ~75 часов, Svix — 8 попыток за ~33 часа (**факт**). Успех — только ответ 2xx, редирект 3xx
   — неудача; таймаут запроса 15–30 с (**факт**). Ответ `410 Gone` — сразу отключить адрес;
   если адрес не принимает ничего 5 суток — отключить и показать администратору (правило Svix,
   **факт**). Ручная повторная отправка и журнал доставок за 30 дней (**вывод** из практики
   Stripe и Svix).
4. **Подпись — Standard Webhooks v1 (HMAC-SHA256).** Заголовки `webhook-id`,
   `webhook-timestamp`, `webhook-signature`; секрет `whsec_` + base64 от 24–64 случайных байт
   (**факт**). Подписывать стоит своими 10 строками на `node:crypto`; официальный пакет npm
   `standardwebhooks` 1.1.1 (2026-08-28, проект жив) — для проверки в тестах и для приёмников,
   которые пишут свой сервис (**факт** о версии, **вывод** о способе применения). Секрет в
   n8n и Make проверяется встроенными средствами HMAC (раздел 3.4).
5. **Тонкое событие с фактами изменения.** В теле — id и тип события, время, id сделки (и
   контакта, платежа…), плюс неизменяемые факты самого события: этап «из» и «в», сумма платежа.
   Полного снимка сделки нет: актуальное состояние автоматизация берёт через API. Так советуют
   Stripe (тонкие события рекомендованы для новых интеграций) и Standard Webhooks (тело до 20 КБ)
   (**факт** об их позиции, **вывод** о нашем формате).
6. **pg-boss 12.38.0** (2026-10-13) — текущая версия, мажорная — 12. Требует Node 22.12+ и
   PostgreSQL 13+; CI проекта гоняет тесты на Node 24 (**факт**). Явной проверки на
   PostgreSQL 18 в документации нет (**не проверено**).

## 1. Таблица исходящих событий (transactional outbox) в PostgreSQL

### 1.1. Суть шаблона

Шаблон описан у Криса Ричардсона: сервис пишет сообщение в таблицу «исходящих» в той же
транзакции, что меняет данные; отдельный процесс-ретранслятор отправляет его дальше. Сообщение
отправится тогда и только тогда, когда транзакция зафиксирована. Ретранслятор может отправить
сообщение больше одного раза (упал после отправки, но до отметки), поэтому получатель должен
быть идемпотентным: помнить id уже обработанных сообщений
([microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html), **факт**).
Варианты ретранслятора там же: опрос таблицы (polling publisher) и чтение журнала транзакций
(transaction log tailing) (**факт**).

### 1.2. pg-boss как очередь в той же транзакции

- Операции pg-boss `send()`, `insert()`, `fetch()`, `complete()` принимают параметр `db` и
  выполняются внутри уже открытой транзакции; при откате транзакции откатывается и задача.
  Для Kysely есть готовый адаптер (**факт**,
  [pg-boss: ORM Transaction Adapters](https://github.com/timgit/pg-boss/blob/master/docs/api/adapters.md)):

  ```ts
  import { fromKysely } from 'pg-boss'
  await db.transaction().execute(async (trx) => {
    await trx.insertInto('orders').values({ item: 'widget', qty: 1 }).execute()
    await boss.send('order-processing', { item: 'widget' }, { db: fromKysely(trx) })
  })
  ```

- Есть и обратное: «транзакционный рабочий» (transactional worker) — pg-boss сам открывает
  транзакцию, и записи обработчика фиксируются вместе с завершением задачи (**факт**, там же).
- Задачи забираются через `SELECT … FOR UPDATE SKIP LOCKED`, рабочие друг друга не блокируют
  (**факт**, [pg-boss README](https://github.com/timgit/pg-boss)).
- **LISTEN/NOTIFY.** В pg-boss это необязательное ускорение поверх опроса: очередь с
  `notify: true` и экземпляр с `useListenNotify` будят рабочих сразу, но опрос продолжает
  работать как страховка, потому что уведомление может потеряться (например, при обрыве
  соединения). Задачи с отложенным стартом уведомления не шлют (**факт**,
  [pg-boss: Workers](https://github.com/timgit/pg-boss/blob/master/docs/api/workers.md),
  [Queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md)). Интервал опроса
  по умолчанию — 2 с (**факт**). Сам PostgreSQL доставляет NOTIFY только после фиксации
  транзакции и только между транзакциями (**факт**,
  [PostgreSQL 18: NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html)). Для внутренней
  CRM задержка до 2 с приемлема, NOTIFY можно не включать (**вывод**).

**Вывод: поток для нашей CRM.**

1. Запрос API или действие менеджера в одной транзакции: меняет сделку, пишет строку в
   `webhook_events` (id, проект, тип, id сущности, тело, время) и ставит задачу pg-boss
   `webhook-fanout` с `{ eventId }` через `fromKysely(trx)`.
2. Рабочий `webhook-fanout` (транзакционный) находит активные адреса проекта, подписанные на
   этот тип, создаёт строки `webhook_deliveries` (событие × адрес) и по задаче `webhook-deliver`
   на каждую.
3. Рабочий `webhook-deliver` отправляет POST, пишет попытку в `webhook_delivery_attempts`
   (код ответа, время, начало тела ответа), при не-2xx бросает ошибку — pg-boss ставит повтор.

Почему не одна задача на событие и адрес сразу в транзакции изменения: тогда транзакция сделки
должна читать настройки адресов и зависеть от них. Шаг fanout отделяет запись события от
маршрутизации (**вывод**). Почему своя таблица, а не только задачи pg-boss: pg-boss удаляет
выполненные задачи через 7 дней и незавершённые через 14 (`deleteAfterSeconds`,
`retentionSeconds`, **факт**), а журнал доставок, ручная повторная отправка и экран
«что ушло автоматизации» нужны дольше и в своём формате (**вывод**).

### 1.3. Ровно один раз невозможен — только хотя бы один раз

- Standard Webhooks: использовать `webhook-id` как ключ идемпотентности, чтобы не обработать
  один вебхук дважды; `webhook-id` одинаков при всех повторах одного сообщения (**факт**,
  [спецификация](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)).
- Stripe: конечная точка иногда получает одно событие больше одного раза; храните id
  обработанных событий (**факт**, [Stripe: Webhooks](https://docs.stripe.com/webhooks)).
- pg-boss сам предупреждает: рабочий, который лишь казался мёртвым, продолжит обработку, и задача
  выполнится дважды, поэтому обработчики должны быть идемпотентными (**факт**,
  [Queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md)).

**Что требовать от приёмника (вывод):** отвечать 2xx быстро, до тяжёлой логики; хранить
`webhook-id` обработанных событий; предпочитать действия, которые безопасно повторить («поставить
этап X»), а не «создать ещё одну задачу». В n8n и Make готового отбрасывания повторов нет —
владелец строит его сам (например, проверкой в своей таблице) (**вывод**: в документации их
узлов вебхуков такой функции не нашли).

### 1.4. Порядок событий одной сделки

- Stripe не гарантирует порядок доставки и прямо просит не зависеть от него; при необходимости
  получатель дочитывает объекты через API (**факт**,
  [Stripe: How events work](https://docs.stripe.com/events/how-events-work)).
- Standard Webhooks порядок не оговаривает (**факт**, в спецификации раздела о порядке нет).
- Make по умолчанию обрабатывает сценарии с мгновенными вебхуками параллельно; последовательную
  обработку включает опция «Process data in order» (**факт**,
  [Make: Webhooks](https://help.make.com/webhooks)). То есть даже упорядоченная отправка не
  гарантирует порядок обработки у владельца (**вывод**).
- У pg-boss с версии 12.10.0 (2026-02-10) есть политика очереди `key_strict_fifo`: строгий
  порядок по `singletonKey`, следующая задача ключа ждёт, пока предыдущая активна, в повторе или
  **окончательно упала**; другие ключи не блокируются. Разблокировать ключ после окончательной
  ошибки — `retry()` или `deleteJob()`, найти такие ключи — `getBlockedKeys()`. Стоимость выборки
  растёт с числом различных ключей в очереди: 200 000 ключей по одной задаче — около 1 с на
  выборку против 0,1 с у обычной очереди (**факт**,
  [Queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md),
  [релиз 12.10.0](https://github.com/timgit/pg-boss/releases/tag/12.10.0)).

**Рекомендация (вывод):** в договоре с приёмником порядок не обещать, как Stripe. Вместо этого
в каждом событии давать время события `occurred_at` и неизменяемые факты («этап из … в …»), а
автоматизации перед действием читать актуальную сделку через API. Если владельцу всё же нужен
порядок, `key_strict_fifo` с ключом `адрес:сделка` даёт его без своего кода; цена — одно событие,
на котором приёмник падает, задерживает все следующие события этой сделки на этот адрес до
исчерпания повторов (до ~3 суток) или ручного вмешательства.

## 2. Повторы, таймауты, отключение адресов, журнал

### 2.1. Что делают другие

| Кто | Расписание повторов | Успех | Таймаут | Отключение | Ручной повтор |
|---|---|---|---|---|---|
| Standard Webhooks | сразу, 5 с, 5 мин, 30 мин, 2 ч, 5 ч, 10 ч, 14 ч, 20 ч, 24 ч — итого ~75 ч, с разбросом (jitter) | 2xx; 3xx — неудача | 15–30 с | ответ `410 Gone` — адрес отключается | — |
| Stripe | до 3 суток, экспоненциально (в тестовом режиме 3 раза за несколько часов) | 2xx | не указан, «отвечайте 2xx быстро» | отключённый адрес перестаёт получать повторы | кнопка Resend — 15 дней; полное тело события — 30 дней |
| Svix | сразу, 5 с, 5 мин, 30 мин, 2 ч, 5 ч, 10 ч, 10 ч | 2xx за 30 с; 3xx — неудача | 30 с | все попытки к адресу неудачны 5 суток → адрес отключается | повтор одного сообщения, «Recover Failed» с даты, «Replay Missing» |
| GitHub | автоматически не повторяет | 2xx за 10 с | 10 с | — | вручную, за последние 3 дня |
| Pipedrive (для сравнения) | 3, 30, 150 с | 2xx | 10 с | 3 дня без успешной доставки → вебхук удаляется | — |

Источники (все — **факт**):
[спецификация Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md),
[Stripe: How events work](https://docs.stripe.com/events/how-events-work),
[Stripe: Webhooks](https://docs.stripe.com/webhooks),
[Svix: Retries](https://docs.svix.com/retries),
[GitHub: Best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks),
[GitHub: Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks),
Pipedrive — из нашего [pipedrive.md](pipedrive.md). Svix хранит тела сообщений 90 дней (на
тарифах от 7 до 90) ([Svix: Payload Retention](https://docs.svix.com/retention), **факт** по
выдаче поиска с этой страницы).

Ещё из спецификации Standard Webhooks (**факт**): редиректы не выполнять, пусть владелец
исправит адрес; держать тело меньше ~20 КБ; против SSRF (запросов к внутренней сети через адрес,
который ввёл пользователь) — отправлять через фильтрующий прокси или из отдельной подсети.

### 2.2. Повторы в pg-boss

Параметры очереди: `retryLimit` (по умолчанию 2), `retryDelay` (секунды, по умолчанию 0),
`retryBackoff` (экспоненциальная пауза, по умолчанию выключена), `retryDelayMax` (потолок паузы).
Формула паузы в коде pg-boss:
`min(retryDelayMax, max(retryDelay,1) × (2^min(16, retry_count+1)/2 × (1 + random())))`
(**факт**, [Queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md) и
`src/plans.ts` в репозитории). После исчерпания повторов задачу можно скопировать в очередь
«мёртвых писем» (`deadLetter`) (**факт**).

**Расчёт (вывод):** `retryDelay: 10`, `retryDelayMax: 21600` (6 ч), `retryLimit: 20` дают паузы
примерно 10–20 с, 20–40 с, … , 3–6 ч, затем по 6 ч — всего около 2,5–3 суток, близко к Stripe и
Standard Webhooks. Точное расписание из таблицы Standard Webhooks pg-boss не даёт; если оно
нужно, рабочий сам ставит следующую попытку через `send(..., { startAfter })`. Для MVP
встроенных повторов достаточно.

Что считать неудачей (вывод, по таблице выше): любой ответ кроме 2xx, включая 3xx, 429 и 5xx;
таймаут 15 с (n8n Cloud и Make отвечают быстрее, раздел 4.3); ошибка сети или TLS.
Исключение — `410 Gone`: адрес сразу отключается, повторы прекращаются.

### 2.3. Отключение, ручная повторная отправка, журнал (вывод)

- Адрес отключается при `410` или если 5 суток подряд ни одна попытка не прошла (правило Svix).
  Администратор проекта видит причину в настройках; ADR 0003 уже называет мониторинг доставки
  частью эксплуатации.
- Рабочий доставки перед отправкой проверяет, что адрес активен; если нет — помечает доставку
  отменённой и не бросает ошибку.
- После включения адреса — кнопка «отправить заново всё неудачное с даты» (как «Recover Failed»
  у Svix) и «отправить это событие ещё раз» в журнале. Повторная отправка сохраняет тот же
  `webhook-id`, чтобы приёмник узнал дубль (**вывод**: спецификация требует один id для
  повторов, про ручные — не говорит).
- Журнал: события, доставки и попытки хранить 30 дней, ночная задача pg-boss удаляет старые
  (ориентир — Stripe: 15 дней повтора и 30 дней полного тела).

## 3. Подпись

### 3.1. Standard Webhooks (рекомендуется)

Спецификация версии 1.0.0, лицензия Apache 2.0
([спецификация](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md),
**факт** для всего пункта):

- Заголовки: `webhook-id` (уникальный id сообщения, одинаковый при повторах),
  `webhook-timestamp` (Unix-время в секундах), `webhook-signature`.
- Подписываемая строка: `{webhook-id}.{webhook-timestamp}.{тело}` — тело байт в байт, «даже
  лишний пробел ломает подпись».
- Подпись: HMAC-SHA256, в заголовке `v1,<base64>`. Несколько подписей — через пробел.
- Секрет: `whsec_` + base64 от 24–64 случайных байт; ключом HMAC служат декодированные байты.
- Смена ключа: какое-то время подписывать и новым, и старым ключом и слать обе подписи;
  приёмник принимает, если совпала любая.
- Защита от повтора: приёмник проверяет, что `webhook-timestamp` в пределах допуска от текущего
  времени. Число в спецификации не задано; в официальной JS-библиотеке — 5 минут
  (`WEBHOOK_TOLERANCE_IN_SECONDS = 5 * 60`).
- Есть асимметричный вариант `v1a` на ed25519 (ключи `whsk_`/`whpk_`) — проверять можно открытым
  ключом. Нам не нужен: n8n и Make умеют HMAC, а ed25519 — нет (**вывод**).
- Тип события: иерархический через точку, символы `[a-zA-Z0-9_]`, например `invoice.paid`.
  Тело рекомендуется вида `{ "type", "timestamp" (ISO 8601), "data" }`.
- Ответ `410 Gone` — приёмник больше не хочет вебхуков, адрес отключается.

### 3.2. Подпись в стиле Stripe (для сравнения)

Заголовок `Stripe-Signature: t=1492774577,v1=<hex>`; подписывается `{t}.{тело}`, HMAC-SHA256,
секрет тоже с префиксом `whsec_`; допуск по времени в библиотеках — 5 минут, ноль запрещён; при
каждом повторе — новые время и подпись; при смене секрета старый можно оставить до 24 часов,
тогда в заголовке несколько `v1=` (**факт**, [Stripe: Webhooks](https://docs.stripe.com/webhooks)).
По защите это то же самое. Отличия Standard Webhooks: id сообщения входит в подпись (защищён от
подмены), формат открыт и одинаков у многих отправителей, есть готовые библиотеки на десятке
языков (**вывод**). Поэтому выбираем Standard Webhooks.

### 3.3. Библиотеки для Node/TypeScript

- **`standardwebhooks`** (npm) — официальная JS/TS-библиотека из репозитория спецификации.
  Последняя версия на npm — 1.1.1 от 2026-08-28 (предыдущая 1.0.0 — 2024-03-04); зависимости
  `fast-sha256`, `@stablelib/base64`. Репозиторий не в архиве, ~1,8 тыс. звёзд, последние коммиты
  в код JS — 2026-10-26…30 (**факт**, реестр npm и GitHub API). API: `new Webhook(secret)`
  (снимает `whsec_` и декодирует base64), `verify(тело, заголовки)` бросает
  `WebhookVerificationError`, `sign(id, дата, тело)` (**факт**,
  [исходник](https://github.com/standard-webhooks/standard-webhooks/blob/main/libraries/javascript/src/index.ts)).
- **Важно:** 2026-10-26 в репозиторий влили исправление разбора заголовка подписи
  ([PR #343](https://github.com/standard-webhooks/standard-webhooks/pull/343)): JS-версия
  делила заголовок по всем запятым и принимала `v1,<подпись>,мусор`. На npm исправление ещё не
  вышло — в `package.json` на main всё та же 1.1.1 (**факт**). Подделать подпись этим нельзя,
  верная подпись всё равно нужна; это лишь мягкий разбор (**вывод**).
- **`svix`** 2.9.1 (2026-10-26) — SDK сервиса Svix, внутри зависит от `standardwebhooks`
  (**факт**, npm). Тянуть SDK внешнего сервиса ради одной функции не нужно (**вывод**).

**Рекомендация (вывод):** подпись на отправке — своя функция на `node:crypto`
(`createHmac('sha256', key).update(`${id}.${ts}.${body}`).digest('base64')`), без
зависимостей. Пакет `standardwebhooks` — в dev-зависимостях: тест проверяет, что его `verify()`
принимает нашу подпись. Его же советовать приёмникам на Node.

### 3.4. Как проверить подпись в n8n и Make

- **n8n:** узел Webhook поддерживает Basic, Header, JWT-аутентификацию и белый список IP, но
  проверки HMAC не имеет; есть опция Raw Body (**факт**,
  [n8n: Webhook node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)).
  Узел Crypto умеет HMAC SHA256 с выводом в BASE64 и HEX, секрет берётся из учётных данных
  «Hmac Secret» (**факт**,
  [n8n: Crypto](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.crypto/)).
  Принимает ли он ключ в виде байтов из base64 — **не проверено**; если нет, остаётся узел Code с
  модулем `crypto`, который на своём сервере n8n разрешается переменной
  `NODE_FUNCTION_ALLOW_BUILTIN` (**факт** о переменной,
  [n8n: Nodes env vars](https://docs.n8n.io/hosting/configuration/environment-variables/nodes/)).
- **Make:** функция `sha256(text; [encoding]; [key]; [key encoding])` при указанном ключе
  возвращает HMAC, вывод в hex, base64 или latin1 (**факт**,
  [Make: Text and binary functions](https://help.make.com/text-and-binary-functions)). Кодировки
  ключа (text, hex, base64, binary) явно перечислены у `sha512`; у `sha256` на странице — нет,
  а выдача поиска с той же справки их приводит (**не проверено** до конца). Заголовки запроса
  доступны в сценарии после опции «Get request headers», тело строкой — «JSON pass-through»
  (**факт**, [Make: Webhooks (apps)](https://apps.make.com/gateway)).
- Подпись считается по точным байтам тела, поэтому приёмнику нужно сырое тело (Raw Body в n8n,
  JSON pass-through в Make) (**вывод**).

**Вывод:** подписывать всегда. Дополнительно разрешить на адресе свои заголовки (например,
`Authorization` со статическим ключом) — для приёмников, которым проще проверить заголовок, чем
HMAC. Так же сделано в Unitalk ([unitalk.md](unitalk.md)) и в n8n («Header auth»).

## 4. Тело события

### 4.1. Тонкое или полное

- Stripe: для новых интеграций — тонкие события. В них тип, id события, время и
  `related_object` (id, тип, URL ресурса); тонкие события не версионируются, потому что
  состояние объекта получатель читает через API. Снимок (snapshot) — когда сторонний инструмент
  требует полный объект; снимок может устареть к моменту обработки и привязан к версии API
  (**факт**, [Stripe: How events work](https://docs.stripe.com/events/how-events-work)).
- Standard Webhooks: полное тело избавляет от лишних вызовов API, тонкое — быстрее, гибче,
  надёжнее на будущее и даёт аудит доступа к данным; тело держать меньше ~20 КБ (**факт**).
- Pipedrive v2 шлёт полное тело `{ meta, data, previous }` (**факт**, [pipedrive.md](pipedrive.md)).
  Сегодня его получают сервер GA и два сервиса расшифровки ([pipedrive-intake-flows.md](pipedrive-intake-flows.md)).

**Рекомендация (вывод):** тонкое событие с фактами изменения, например

```json
{
  "type": "deal.stage_changed",
  "timestamp": "2026-11-04T10:15:00Z",
  "data": {
    "event_id": "evt_…",
    "project_id": "…",
    "deal_id": "…",
    "from_stage_id": "…",
    "to_stage_id": "…",
    "actor": { "type": "api_key", "id": "…" }
  }
}
```

Факты события («из какого этапа в какой», сумма и валюта платежа, исход звонка) не меняются со
временем и не устаревают, в отличие от снимка сделки. Всё прочее автоматизация читает через
`GET /deals/{id}`. Поле `actor` нужно, чтобы автоматизация не реагировала на собственные изменения
и не уходила в цикл. Для GA и сервисов расшифровки, которым нужны поля сделки, — один лишний
запрос к API либо узкое расширение позже.

### 4.2. Имена и версии типов (вывод)

Имена по Standard Webhooks: `deal.created`, `deal.stage_changed`, `deal.won`, `deal.lost`,
`registration.added`, `payment.succeeded`, `payment.refunded`, `call.completed`, `call.missed`,
`task.completed`. Изменения тела — только добавлением полей. Ломающее изменение — новый тип
(`deal.stage_changed.v2`) рядом со старым, пока подписчики не перейдут. Тонкое тело меняется
редко, в этом и смысл совета Stripe.

### 4.3. Что ждут n8n и Make

| | n8n (узел Webhook) | Make (Custom webhook) |
|---|---|---|
| Формат | JSON, XML (Raw Body), бинарные данные (**факт**) | JSON, form-data, query string (**факт**) |
| Максимум тела | 16 МБ, `N8N_PAYLOAD_SIZE_MAX` (**факт**) | 5 МБ (**факт**) |
| Ответ | «Immediately» (сразу), после последнего узла, или узел «Respond to Webhook» (**факт**) | по умолчанию сразу `200 Accepted`, запрос встаёт в очередь (**факт**) |
| Время на ответ | n8n Cloud за Cloudflare: нет ответа за 100 с — ошибка 524 (**факт**) | модуль ответа — 180 с, потом `200 Accepted` (**факт**; другая статья справки называет 40 с — **противоречие**) |
| Ограничения | белый список IP, ответ 403 (**факт**) | 300 запросов за 10 с, дальше 429; очередь полна — 400 «Queue is full»; вебхук без сценария 5 суток — отключается, ответ 410 (**факт**) |
| Проверка подписи | нет встроенной; узел Crypto или Code (**факт**) | нет встроенной; функция `sha256` с ключом (**факт**) |
| Порядок | — | по умолчанию параллельно, опция «Process data in order» (**факт**) |

Источники: [n8n: Webhook node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/),
[n8n: Common issues](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/common-issues/),
[n8n: Endpoints env vars](https://docs.n8n.io/hosting/configuration/environment-variables/endpoints/),
[Make: Webhooks](https://help.make.com/webhooks), [Make: Webhooks (apps)](https://apps.make.com/gateway).

**Выводы для нас:** отправлять `application/json; charset=utf-8`; таймаут 15 с хватает, если в
n8n выбран ответ «Immediately», а в Make не используется модуль ответа; 429 и 400 от Make — обычная
неудача с повтором; `410` от Make совпадает с правилом Standard Webhooks — адрес отключаем.

## 5. pg-boss

- **Версия:** 12.38.0 от 2026-10-13, выходит часто (12.35–12.38 за две недели); репозиторий
  активен (последний push 2026-11-04), ~4,1 тыс. звёзд (**факт**, npm и GitHub API).
- **Мажорные версии:** 12.0.0 (2025-11-09) — переход на ESM и TypeScript, экспорт по имени
  `import { PgBoss } from 'pg-boss'`; 11.0.0 (2025-09-26) — без автоматической миграции с v10
  (**факт**, [релизы](https://github.com/timgit/pg-boss/releases)). Нам не важно: начинаем с 12.
- **Требования:** Node 22.12+ (в `package.json`: `"node": ">=22.12.0"`) и PostgreSQL 13+
  (**факт**, [документация](https://github.com/timgit/pg-boss/blob/master/docs/index.md)).
  CI проекта запускает тесты на Node 24 с образом `postgres` без закреплённой версии (**факт**,
  `.github/workflows/ci.yml`). Совместимость с PostgreSQL 18 следует из «13 или выше» и из
  того, что в документации есть пример Citus на PostgreSQL 18 (**вывод**); прямого заявления
  «проверено на 18» нет (**не проверено**).
- **Схема:** pg-boss создаёт свою схему `pgboss`; нужно право `CREATE` на базу, либо SQL
  выгружается CLI (`--dry-run`, `plans`) и применяется вручную (**факт**,
  [Install](https://github.com/timgit/pg-boss/blob/master/docs/install.md)). Для наших миграций
  второй путь удобнее: схема pg-boss видна в репозитории (**вывод**).
- **Очереди:** создаются явно `createQueue(name, options)`; политики `standard`, `short`,
  `singleton`, `stately`, `exclusive`, `key_strict_fifo`; политику после создания поменять нельзя
  (**факт**, [Queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md)).
- **Повторы и хранение:** `retryLimit`, `retryDelay`, `retryBackoff`, `retryDelayMax`,
  `deadLetter`, `expireInSeconds`, `heartbeatSeconds`, `retentionSeconds` (14 дней),
  `deleteAfterSeconds` (7 дней) — на очереди, с переопределением на задаче (**факт**, там же).
- **Ключи:** `singletonKey` на задаче — для ограничений «одна задача на ключ» в политиках
  `short`/`singleton`/`stately`/`exclusive` и для порядка в `key_strict_fifo` (**факт**,
  [Jobs](https://github.com/timgit/pg-boss/blob/master/docs/api/jobs.md)).

**Настройки для старта (вывод):**

```ts
await boss.createQueue('webhook-fanout', { retryLimit: 5, retryBackoff: true })
await boss.createQueue('webhook-deliver', {
  policy: 'standard',          // порядок не обещаем; key_strict_fifo — если владелец попросит
  retryLimit: 20, retryDelay: 10, retryBackoff: true, retryDelayMax: 6 * 3600,
  expireInSeconds: 60,         // запрос с таймаутом 15 с плюс запас
})
```

## Не проверено

- Работа pg-boss именно на PostgreSQL 18 — только «PostgreSQL 13 или выше» и незакреплённый
  образ в CI. Проверить нашим тестом при подключении pg-boss.
- Принимает ли узел Crypto в n8n ключ HMAC в base64 (байты), а не строкой. Если нет — узел Code.
- Кодировка ключа у функции `sha256` в Make: на странице справки перечислена только у `sha512`.
  Проверить на живом сценарии.
- Время ответа модуля Make «Webhook response»: 180 с в документации приложений, 40 с в одной
  статье справки.
- Когда исправление разбора заголовка подписи (PR #343) выйдет на npm в `standardwebhooks`.
- Расчёт итогового окна повторов pg-boss (~2,5–3 суток) сделан по формуле из кода, не прогоном.
- Срок хранения тел у Svix (90 дней) — по выдаче поиска с их страницы, страницу целиком не читали.
