# Стек, хостинг и требования к объёму для своей CRM

- **Дата исследования:** 2026-11-03.
- **Вопрос:** на каком стеке и где строить CRM. Её пишет один владелец вместе с Claude Code.
  Уклон — TypeScript везде и PostgreSQL. Объём — сотни тысяч сделок (сейчас около 86 тыс. открытых, рост),
  около 30 пользователей. Нужны: пользовательские поля через конструктор, входящие вебхуки WayForPay
  (платёжный сервис) и Ringostat (телефония), фоновые задачи (курсы НБУ, автоматика воронки),
  интерфейс на украинском и русском, адаптивный веб.
- **Источники:** только первичные — официальная документация, страницы цен, GitHub-репозитории и
  страницы релизов. Ссылка стоит у каждого утверждения.
- **Пометки:** «**не проверено**» — факт не удалось подтвердить первичным источником.
  «**расхождение**» — первичные источники противоречат друг другу. «**оценка**» — мой расчёт, а не цифра
  из источника. Разделы 8–10 — мой синтез.
- **Цены** — на 2026-11-03, в валюте страницы, без НДС, если не сказано иное. Цены меняются, перед
  заказом их нужно перепроверить.
- Контекст о текущем Pipedrive взят из `docs/research/our-pipedrive.md` (осмотр аккаунта 2026-11-03):
  тариф Professional, 32 места по €59, около €1 890 в месяц; 29 активных пользователей; 174 из 300
  настраиваемых полей заняты; около 86 тыс. открытых сделок в воронке «ALPI».

## TL;DR — рекомендация

Один сервер Hetzner Cloud в ЕС. На нём в Docker Compose работают PostgreSQL 18, API, обработчик
фоновых задач и обратный прокси. Код — один TypeScript-монорепозиторий:

| Слой | Выбор | Почему коротко |
|------|-------|----------------|
| Бэкенд и вебхуки | **Hono** на Node.js | Лёгкий HTTP-сервер, типизированный RPC-клиент для фронтенда |
| Фронтенд | **React SPA на Vite** + TanStack Router + TanStack Query | Внутренний инструмент за логином: SSR не нужен, интерфейс почти весь интерактивный (канбан, таблицы, массовые операции) |
| Доступ к БД | **Kysely** + kysely-codegen | SQL-подход, удобен для динамических фильтров по пользовательским полям в JSONB |
| Пользовательские поля | **JSONB-колонка** + таблица описаний полей + GIN-индекс | EAV отброшен, см. раздел 3 |
| Аутентификация | **Better Auth** (плагин admin) | Роли, бан, отзыв сессий, имперсонация; встроенный адаптер Kysely для PostgreSQL |
| Фоновые задачи | **pg-boss** | Очередь в том же PostgreSQL: cron, повторы, очередь «мёртвых» задач |
| i18n | **i18next / react-i18next** | Стандарт для React SPA |
| Хостинг | **Hetzner Cloud CX43** (8 vCPU / 16 GB) + бэкапы Hetzner + копия дампов вне сервера | Около €20 в месяц против €1 890 за Pipedrive |

Второй вариант, если не хочется администрировать PostgreSQL самому: тот же код, но база — управляемый
PostgreSQL (DigitalOcean во Франкфурте или Supabase Pro в ЕС). Это от $30 до $85 в месяц.

## 1. Фреймворк

### 1.1 Next.js (App Router)

- Последняя стабильная версия — **16.4.5** от 2026-11-03. В этом выпуске семь исправлений безопасности
  средней тяжести: утечки кэша, раскрытие cookie, обход проверки SVG, внедрение в ответ
  ([релизы Next.js](https://github.com/vercel/next.js/releases)).
- В декабре 2025 года в React Server Components нашли уязвимость **CVE-2025-55182** с оценкой CVSS 10.0:
  удалённое выполнение кода без аутентификации. Уязвимы Next.js и React Router в режимах с RSC. Затем
  нашли ещё DoS и раскрытие исходного кода, в том числе CVE-2026-23864 от 26 января 2026 года
  ([блог React](https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components)).
- Self-hosting через `next start` официально поддерживается. Оптимизация изображений и Proxy (бывший
  middleware) работают без настройки. Перед сервером рекомендуют ставить обратный прокси, например nginx
  ([Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting)).
- Подводные камни при нескольких экземплярах сервера:
  - кэш по умолчанию лежит на локальном диске каждого экземпляра;
  - для Server Functions нужен общий ключ `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`;
  - для защиты от расхождения версий при раскатке нужен `deploymentId`;
  - для согласованной инвалидации кэша по тегам нужен свой cache handler, например на Redis.

  Всё это — из того же [руководства по self-hosting](https://nextjs.org/docs/app/guides/self-hosting).
- Вебхуки делаются через Route Handlers. i18n — через next-intl. next-intl поддерживает App Router,
  Server Components, синтаксис ICU и множественные формы ([next-intl](https://next-intl.dev/)).
  Совместимость с Next.js 16 на главной странице next-intl не указана — **не проверено**.

### 1.2 React Router (бывший Remix), режим framework

- Последняя стабильная версия на странице релизов — **8.5.1**
  ([релизы React Router](https://github.com/remix-run/react-router/releases)). Минимальная версия Node
  для v8 — **не проверено**.
- Три режима: declarative, data и framework. В framework-режиме есть загрузчики (`loader`), действия
  (`action`) и типизированные модули маршрутов. Есть SPA, SSR и SSG. Resource routes подходят для
  вебхуков ([Modes](https://reactrouter.com/start/modes)).

### 1.3 TanStack Start

- На сайте помечена версия **v1 Latest**, то есть 1.0 стабильна. Есть SSR, стриминг, серверные функции
  и «server routes for outside callers», то есть HTTP-эндпоинты. Одна из целей развёртывания — Node.js
  ([TanStack Start](https://tanstack.com/start/latest)).

### 1.4 Hono + SPA (рекомендуется)

- Последняя версия Hono — **4.13.16**. Это выпуск с исправлениями безопасности: обход пути в `mount()`,
  wildcard-middleware, `csrf()`. Есть пре-релизы **5.0.0-rc** ([релизы Hono](https://github.com/honojs/hono/releases)).
- Hono работает на Node через адаптер `@hono/node-server` ([Node.js](https://hono.dev/docs/getting-started/nodejs)).
  RPC-режим отдаёт клиенту типы маршрутов сервера. Фронтенд получает типизированные вызовы API без
  генерации кода ([RPC](https://hono.dev/docs/guides/rpc)).
- Фронтенд — Vite + TanStack Router (типизированные маршруты) и TanStack Query (кэш запросов)
  ([TanStack Router](https://tanstack.com/router/latest)).
- NestJS в таблицу не включён. Подробности — в разделе 9.

### 1.5 Сравнение для нашего случая

| Критерий | Next.js 16 | React Router 8 (framework) | Hono + Vite SPA |
|----------|-----------|---------------------------|-----------------|
| Нужен ли нам SSR | Нет: всё за логином | Нет | Нет, его и нет |
| Сложность модели | RSC, Server Actions, несколько слоёв кэша | Средняя | Низкая: REST/RPC API + клиент |
| Поверхность уязвимостей | RSC: CVE-2025-55182 и далее; 7 исправлений в 16.4.5 | RSC-режим затронут той же CVE | RSC нет; патчи Hono тоже бывают |
| Вебхуки и обработчик задач | Route Handlers; обработчик — отдельный процесс | Resource routes; обработчик — отдельно | Тот же код Hono; обработчик — второй entrypoint того же пакета |
| Знакомство Claude Code | Очень высокое | Высокое | Высокое |

## 2. ORM и конструктор запросов

| | Prisma | Drizzle | Kysely |
|-|--------|---------|--------|
| Стабильная версия | **7.10.1**; есть пре-релиз **8.0.0-rc.22** ([релизы](https://github.com/prisma/prisma/releases)) | **0.45.4**; **1.0.0-rc.5** с большим числом несовместимых изменений ([релизы](https://github.com/drizzle-team/drizzle-orm/releases)) | **0.29.8** ([релизы](https://github.com/kysely-org/kysely/releases)) |
| JSONB | Фильтры по `path`, `string_contains`, `array_contains`. JSON не типизирован. Нельзя выбрать часть JSON, фильтровать по наличию ключа, сортировать свойства ([Working with Json](https://www.prisma.io/docs/orm/prisma-client/special-fields-and-types/working-with-json-fields)) | `jsonb().$type<T>()` — типы только на этапе компиляции, данные во время выполнения не проверяются ([PG column types](https://orm.drizzle.team/docs/column-types/pg)) | Любой SQL-оператор через `sql`; хелперы `jsonArrayFrom` / `jsonObjectFrom` для вложенных связей ([Relations](https://kysely.dev/docs/recipes/relations)) |
| Схема | Свой язык схемы + миграции | Схема в TS + drizzle-kit | Типы генерирует kysely-codegen из живой БД; миграции на SQL или через Migrator |
| Риск на ближайший год | Мажорная версия 8 на подходе | Переход 0.x → 1.0 с несовместимыми изменениями | Версия 0.x, но API стабилен (**оценка**) |

Почему Kysely. Экран «фильтры по пользовательским полям» собирает SQL динамически: поле, оператор,
значение. В Kysely это обычная композиция запроса. Better Auth подключается к PostgreSQL через
встроенный адаптер Kysely ([Better Auth: PostgreSQL](https://www.better-auth.com/docs/adapters/postgresql)).
pg-boss умеет ставить задачи внутри транзакции через адаптер Kysely ([pg-boss](https://pgboss.io/)).
Так весь стек сходится на одном инструменте доступа к БД.

## 3. Пользовательские поля: JSONB или EAV

### Факты из документации PostgreSQL

- `jsonb` хранится в разобранном бинарном виде: запись чуть медленнее, обработка значительно быстрее,
  потому что текст не разбирается заново ([JSON Types](https://www.postgresql.org/docs/current/datatype-json.html)).
- GIN-индекс с классом операторов по умолчанию `jsonb_ops` поддерживает операторы `?`, `?|`, `?&`,
  `@>`, `@?`, `@@`. Класс `jsonb_path_ops` не поддерживает проверку наличия ключа (`?`), но обычно
  намного меньше и быстрее на поиске по вхождению `@>` ([JSON Types, 8.14.4](https://www.postgresql.org/docs/current/datatype-json.html)).
- Можно индексировать выражение, то есть отдельный ключ, например `(custom -> 'tags')` или
  `(custom ->> 'utm_source')` ([JSON Types](https://www.postgresql.org/docs/current/datatype-json.html),
  [Indexes on Expressions](https://www.postgresql.org/docs/current/indexes-expressional.html)).

### Сравнение (синтез)

| Критерий | JSONB-колонка `custom` у сделки | EAV: таблица `deal_field_values(deal_id, field_id, value_*)` |
|----------|-------------------------------|------------------------------------------------------------|
| Строк в БД | 1 строка на сделку | Сделки × заполненные поля. **Оценка:** 500 тыс. сделок × 40 полей = 20 млн строк |
| Чтение карточки и списка | Одна строка, без JOIN | JOIN или агрегация на каждое поле |
| Фильтр «поле = значение» | `@>` по GIN `jsonb_path_ops` или индекс выражения на горячее поле | Индекс `(field_id, value)`; фильтр по нескольким полям — несколько JOIN или INTERSECT |
| Сортировка по полю | По выражению `custom->>'x'`, при необходимости с индексом выражения | JOIN на каждую сортировку |
| Типы значений | Проверка в приложении по описанию поля; тип для сравнения задаётся приведением | Отдельные колонки `value_text`, `value_num`, `value_date`; строже, но громоздко |
| Изменение конструктором | Новое поле — только строка в `field_definitions`, без DDL | То же |
| История изменений | Diff старого и нового JSON при записи | Естественно, по строкам |

**Решение:** JSONB. Описания полей (тип, подпись на uk/ru, варианты списка, обязательность по этапам)
хранятся в таблице `field_definitions`. Значения — в `deals.custom jsonb` с ключом `id` поля, а не его
подписью. На всю колонку — GIN `jsonb_path_ops`. На 5–10 самых нагруженных полей (например UTM-метки
и дата вебинара) — индексы выражений. Если поле становится «системным», его переносят в обычную
колонку миграцией.

## 4. Аутентификация

- **Better Auth.** Последняя версия — **1.7.16**
  ([релизы](https://github.com/better-auth/better-auth/releases)). Этот выпуск закрывает несколько
  уязвимостей: отозванные сессии оставались рабочими при кэше cookie; ссылки подтверждения email не
  были привязаны к аккаунту; wildcard trusted origins совпадали с лишними хостами. Значит, версию
  нужно держать на последнем патче и следить за security advisories в репозитории.
- Плагин admin:
  - создание пользователей администратором;
  - роли и свои права с проверкой `hasPermission`;
  - бан, который сразу отзывает все сессии;
  - список и отзыв сессий;
  - имперсонация («войти как сотрудник»), по умолчанию на 1 час.

  Плагину нужна миграция БД ([Admin plugin](https://www.better-auth.com/docs/plugins/admin)).
- PostgreSQL подключается через встроенный адаптер Kysely и `pg.Pool`. CLI генерирует и применяет
  схему ([PostgreSQL adapter](https://www.better-auth.com/docs/adapters/postgresql)).
- **Auth.js (NextAuth).** С 22 сентября 2025 года его сопровождает команда Better Auth. Для существующих
  пользователей обещаны патчи безопасности и срочные исправления. Новым проектам прямо советуют
  начинать с Better Auth ([анонс](https://www.better-auth.com/blog/authjs-joins-better-auth)).
- **Lucia.** Библиотека объявлена устаревшей в марте 2025 года. Вместо npm-пакета сайт даёт один файл
  `auth_session.ts` для копирования в проект и ссылку на учебник Auth Book ([lucia-auth.com](https://lucia-auth.com/)).
  «Lucia-подход» — это свои сессии в своей таблице, примерно 100–200 строк кода (**оценка**).

## 5. Фоновые задачи

| | pg-boss | graphile-worker | BullMQ |
|-|---------|-----------------|--------|
| Хранилище | PostgreSQL 13+, Node 22.12+ ([pgboss.io](https://pgboss.io/)) | PostgreSQL + Node ([worker.graphile.org](https://worker.graphile.org/)) | По умолчанию Redis 6.2+, а также Valkey и Dragonfly. Есть необязательный PostgreSQL-бэкенд 13+, но «Redis остаётся самым проверенным вариантом», а пропускная способность на PostgreSQL обычно ниже ([docs](https://docs.bullmq.io/), [PostgreSQL backend](https://docs.bullmq.io/guide/postgresql)) |
| Версия | **12.38.0** ([релизы](https://github.com/timgit/pg-boss/releases)) | **не проверено** | **не проверено** |
| Захват задач | `SKIP LOCKED`, задачи ставятся внутри транзакции приложения; адаптеры Drizzle, Knex, Kysely, Prisma | LISTEN/NOTIFY — старт за миллисекунды; до 10 000 задач в секунду | — |
| Cron | cron и RRULE | cron с точностью до минуты | Job Schedulers (cron или интервал) |
| Повторы | Экспоненциальная задержка, очереди «мёртвых» задач с повторным запуском | Автоматические повторы с экспоненциальной задержкой | Встроенные или свои стратегии задержки |
| Прочее | Rate limit, debounce, приоритеты, зависимости задач, веб-панель, OpenTelemetry | Отложенные задачи, debounce, отмена | Flows (родитель–потомки), дедупликация, rate limit |

**Выбор — pg-boss.** Нет второго хранилища. Задачу «обработать вебхук» можно поставить в той же
транзакции, что и запись события. Есть очередь «мёртвых» задач и веб-панель. graphile-worker — почти
равная альтернатива. Её довод — задачи можно ставить из SQL-триггеров.

Нужные задачи (синтез): ежедневный курс НБУ по cron; обработка входящих вебхуков с повторами;
правила автоматики воронки, например «при переходе на этап X создать задачу»; массовая передача
сделок ушедших менеджеров (на них сейчас 339 открытых сделок, по `our-pipedrive.md`); импорт из Pipedrive.

## 6. Входящие вебхуки

- **WayForPay** присылает уведомление на `serviceUrl`. Подпись — HMAC_MD5 секретным ключом от строки
  `merchantAccount;orderReference;amount;currency;authCode;cardPan;transactionStatus;reasonCode`.
  Мерчант должен ответить JSON с `orderReference`, `status: "accept"`, `time` и подписью HMAC_MD5 от
  `orderReference;status;time`. Без правильного ответа WayForPay шлёт запросы **4 дня** или до получения
  правильного ответа ([WayForPay wiki](https://wiki.wayforpay.com/en/view/852102)).
  Значит, обработчик должен:
  1. проверить подпись;
  2. записать сырое событие в таблицу входящих событий, идемпотентно по `orderReference` и статусу;
  3. поставить задачу в pg-boss;
  4. сразу вернуть подписанный `accept`.
- **Ringostat** шлёт вебхуки на события:
  - входящий звонок: до звонка, после, при ответе, при переадресации;
  - исходящий звонок;
  - отправка формы на сайте;
  - диалог в мессенджере;
  - создание или изменение сделки.

  Метод — GET, POST или PUT. Формат — JSON, raw, JSON-RPC или form. Заголовки можно править, то есть
  можно добавить свой токен для проверки ([Ringostat: webhooks](https://help.ringostat.com/en/articles/6313229-how-to-realise-the-ringostat-integration-using-webhooks),
  [Incoming call event](https://help.ringostat.com/en/articles/6559993-webhooks-incoming-call-event)).
  - **Расхождение** о повторах. Одна статья говорит, что при ответе 4XX–5XX вебхук отправят ещё 3 раза
    ([Actions with errors](https://help.ringostat.com/en/articles/6559968-webhooks-actions-with-errors), видно
    только по фрагменту в поиске). Другая — что без ответа 200 OK повторных попыток не будет
    ([руководство по интеграции](https://help.ringostat.com/en/articles/6313229-how-to-realise-the-ringostat-integration-using-webhooks)).
    Вывод: отвечать 200 сразу после записи события, обработку делать в фоне.
  - Список IP-адресов Ringostat для белого списка — **не проверено**.

## 7. i18n и адаптивность

- **i18next**, последняя версия **26.7.1** ([релизы](https://github.com/i18next/i18next/releases)). Для
  React — react-i18next.
- В украинском и русском три формы множественного числа: one, few, many. Их нужно проверить на тестах
  форматирования (синтез).
- Даты, числа и валюты (EUR, USD, UAH) форматируются через `Intl` (синтез).
- Адаптивная вёрстка от фреймворка не зависит. Её задача — UI-кит и CSS (синтез). Канбан с 86 тыс.
  сделок на первом этапе требует серверной пагинации колонок, а не загрузки всего этапа.

### 8.5 Объём (оценка)

- Сделки: сейчас около 90 тыс. открытых во всех воронках, плюс закрытые. Расчёт на 500 тыс.–1 млн за
  несколько лет.
- Строка сделки с JSONB на 40–60 заполненных полей — 2–4 KB. Это 1–4 GB на сделки. Активности, заметки,
  история изменений, события вебхуков и звонков дадут ещё в разы больше. Итого 5–30 GB за 2–3 года.
- 30 пользователей — это десятки запросов в секунду в пике. Для PostgreSQL на 8 vCPU / 16 GB это малая
  нагрузка. Узкие места — тяжёлые отчёты и массовые операции, а не число пользователей.
- PostgreSQL 18 — текущая мажорная версия, минорная 18.6, поддержка до 14 ноября 2030 года. Каждую
  мажорную версию поддерживают 5 лет ([Versioning](https://www.postgresql.org/support/versioning/)).

## 9. Рекомендация и обоснование (синтез)

1. **Hono API + React SPA на Vite в одном монорепозитории.** Внутренней CRM за логином не нужен SSR.
   Без RSC меньше движущихся частей и меньше поверхность атаки: в RSC была CVE-2025-55182 с CVSS 10.0
   и ещё четыре уязвимости после неё. Вебхуки, API и обработчик задач — один TypeScript-пакет с двумя
   точками входа. Типы API доходят до клиента через Hono RPC.
2. **Kysely + kysely-codegen.** Динамические фильтры по пользовательским полям в JSONB — это SQL, и
   Kysely его не прячет. Better Auth и pg-boss подключаются к нему напрямую.
3. **Пользовательские поля в JSONB.** Плюс таблица описаний полей, GIN `jsonb_path_ops` и индексы
   выражений на горячие поля. EAV не берём.
4. **Better Auth** с плагином admin. Регистрации нет: пользователей создаёт администратор. Нужны роли,
   бан ушедших менеджеров с отзывом сессий и имперсонация для поддержки. Версию держать на последнем
   патче.
5. **pg-boss** в том же PostgreSQL. Отдельный Redis не нужен.
6. **Вебхуки** пишутся в таблицу входящих событий идемпотентно, получают быстрый ответ, а
   обрабатываются фоновой задачей. Для WayForPay ответ — подписанный `accept`.
7. **i18next**, языки uk и ru. Подписи пользовательских полей хранятся на двух языках в описании поля.
8. **Hetzner Cloud CX43** (Германия или Финляндия) под Docker Compose: PostgreSQL 18, API, обработчик
   задач, обратный прокси с TLS. Бэкапы Hetzner (+20 %) и ежедневный `pg_dump` или архив WAL в
   хранилище вне сервера. Развёртывание — `docker compose` из CI или Coolify на том же сервере.
   Около €20–25 в месяц.

## 10. Что отбросили и почему

- **Next.js** — сильный второй вариант. Отброшен потому, что для внутреннего инструмента его главная
  ценность (SSR, RSC, кэш) не нужна, а цена есть:
  - сложная модель кэширования;
  - отдельные требования при нескольких экземплярах;
  - частые исправления безопасности: 7 в одном выпуске 16.4.5, критическая RCE в RSC в декабре 2025.

  Если владелец уже хорошо знает Next.js, это приемлемый выбор. Тогда — Route Handlers для вебхуков и
  отдельный процесс для pg-boss.
- **React Router 8 (framework) и TanStack Start.** Рабочие варианты. Но они добавляют серверный
  рендеринг, который нам не нужен. Для React Router не проверена минимальная версия Node.
- **NestJS.** Тяжёлый каркас на декораторах и DI. Для одного разработчика это много шаблонного кода
  без выгоды (синтез; версия NestJS — **не проверено**).
- **Prisma.** Слабая работа с JSON: нет фильтра по наличию ключа, JSON не типизирован, нет выбора
  части JSON. Кроме того, на подходе мажорная версия 8.
- **Drizzle.** Хороший вариант. Отброшен из-за перехода на 1.0 с большим списком несовместимых
  изменений (сейчас 1.0.0-rc.5). Можно вернуться к нему после выхода 1.0.
- **EAV для пользовательских полей.** Десятки миллионов строк и JOIN на каждое поле в фильтре и
  сортировке. Выгоды по сравнению с JSONB и таблицей описаний полей нет.
- **Auth.js.** Режим сопровождения: только патчи безопасности. Сами сопровождающие советуют новым
  проектам Better Auth.
- **Lucia.** Библиотека устарела. Её подход — свои сессии в одном файле — остаётся запасным планом,
  если Better Auth начнёт мешать.
- **BullMQ.** Нужен Redis, то есть второе хранилище для бэкапа и мониторинга. PostgreSQL-бэкенд у
  BullMQ есть, но сами авторы называют Redis более проверенным.
- **PaaS (Railway, Fly, Render) и Neon как основа.** В 3–5 раз дороже одного сервера Hetzner при нашей
  постоянной нагрузке. Для PaaS не проверено, где лежат данные в ЕС. Засыпание базы в Neon для
  CRM, которой пользуются весь рабочий день, выгоды не даёт.
- **Supabase целиком** (его Auth, API и хранилище). Привязывает к платформе. Как просто управляемый
  PostgreSQL он годится для варианта C.

## 11. Пробелы и непроверенное

- Можно ли сейчас заказать Hetzner CX в Германии или Финляндии: на странице есть «Currently not available».
- Цены Render, Aiven, Scaleway. Регион ЕС у Railway и DigitalOcean. Бэкапы и PITR у DigitalOcean.
- Цена хранилища для внешних дампов (Hetzner Storage Box или Object Storage).
- Версии graphile-worker, BullMQ и NestJS. Минимальная версия Node для React Router 8.
- Совместимость next-intl с Next.js 16 (нужна только при выборе Next.js).
- Повторы вебхуков Ringostat (**расхождение** между статьями), его IP-адреса и полный список параметров
  события.
- Задержка от Украины до Фалькенштейна, Нюрнберга и Хельсинки не измерялась.
- Требования к хранению персональных данных клиентов (GDPR, украинский закон о защите персональных
  данных) не исследовались.
- Размер БД — оценка. Его нужно уточнить после пробного импорта из Pipedrive.
